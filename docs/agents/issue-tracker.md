# Issue tracker: GitHub Issues

## 正式任务来源

- 仓库：<https://github.com/jking412/Noterion>。
- 工单：<https://github.com/jking412/Noterion/issues>。
- GitHub Issue 是任务内容、依赖、讨论、验收和开关状态的正式来源。发布、读取和更新工单时使用 GitHub 接口；不要再创建一套本地实施工单作为并行真相源。
- 规格、研究与技术记录继续存放在 `.scratch/<feature-slug>/`。根 `CONTEXT.md` 和 `docs/adr/` 的职责不变。
- 本地任务计划与 Issue 索引用于导航，修改任务要求时以最新 Issue、用户明确指示及其引用依据核对。

## 工单约定

- 一项任务一个 Issue，写明类型、交付行为或待回答问题、可勾选的验收条件和 Blocked by。
- 类型包括原型、询问、技术验证和实施；类型写在正文，分流使用 `triage-labels.md` 中的五个标签。
- 依赖优先使用 GitHub 原生 blocked-by 关系，并在正文中列出阻塞 Issue 的编号、标题和链接。若当前工具无法维护原生依赖，正文链接仍须完整，并如实记录能力限制。
- `ready-for-agent` 表示内容足够明确，不表示可忽略尚未完成的依赖。所有阻塞均已解决后才能领取。
- 需要用户决定的询问使用 `ready-for-human`；代理可以准备示例与推荐，用户明确回答前不能认定完成。
- 新结果、问题与证据记录在对应 Issue 的评论或正文。关闭前核对本 Issue 的验收，不以有提交、编译成功或代理完成信号单独替代验收。
- 原型制作完成与用户选定方案分别验收。技术验证要形成可用且可复现的路径；只有失败报告不能解除后续实施阻塞。

## 执行顺序

从尚未完成且无阻塞的任务中选择。独立分支可以并行；共享接口、迁移或验证资源冲突时协调执行与整合。

主要功能优先。完整故障演练和图谱重建维护能力仍在范围内，安排在主要功能之后；基本持久化、同步可靠性和真实错误反馈随各功能交付。

## 探索与后续发现

原型、询问或技术验证发现新问题时，在对应 Issue 记录问题、事实和影响。只有能明确描述的问题才新建探索 Issue，仅阻塞受影响分支；未确认的用户决定不能由代理代答。需要规划索引时保存在功能目录中，并链接到 GitHub Issues，避免复制工单全文形成第二套状态。

普通工单状态使用 GitHub open/closed，分流使用五个标签。原本本地 Wayfinder 专用的 claimed/resolved 字段不应用于这些 GitHub 工单；自动领取与执行记账方式由开发自动化方案另行落实。
