# Desktop media: official basis and validation limits

2026-11-12. This note supports Issue #21's real WebView2 validation; it does not substitute for running the application.

Microsoft documents WebView2 local PDF navigation and a built-in PDF viewer. Its PDF toolbar supports page selection, zoom and other controls. This supports first trying an `application/pdf` response in the desktop viewer; it does **not** prove that a particular cross-origin iframe, CSP or WebView2 build will render correctly. The acceptance must inspect the actual embedded PDF, not merely the iframe `load` event. Sources: [local content](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/working-with-local-content), [PDF viewer API](https://learn.microsoft.com/en-us/microsoft-edge/webview2/reference/win32/icorewebview2settings7).

The WebView2 local-content documentation explains that resources presented through HTTP(S) URLs follow the supplied response headers and normal origin rules. The application can provide a tokenized loopback HTTP URL from its own process and stream managed files without passing file bytes through Tauri IPC. The endpoint must restrict access to the selected managed resource, implement CORS for the actual embedded-page origin and set the required media/frame CSP sources. This is an engineering inference from those documented semantics; real startup, seek and PDF rendering remain empirical acceptance requirements. No persistent external service is required.

[RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html#section-14) defines byte ranges, `206`, `Content-Range` and `416`. The runner should compare a literal distant interval to independently read source bytes, consume and hash one ordinary GET, and cancel another ordinary GET after a small received interval. An open-ended Range request does not mean the complete range was read: record actual read/write bytes and cancellation. A bounded streaming buffer is not a limit on total WebView/OS memory.

Use the existing synthetic 1,277,422,426-byte H.264/AAC MP4, VP9/Opus WebM and FFV1/PCM MKV. Their actual files, probe output and generation/decode evidence are in `.scratch/personal-knowledge-graph/validation/video-playback/`. Their previous object-service playback is historical evidence only. Re-run through the formal local-file resource entry. FFV1's audio-only demux on this Runtime requires checking video dimensions/decoded frames as well as `video.error`.

If actual embedded PDF rendering fails, bundle a PDF renderer and its worker locally; do not load a CDN script or label a blank iframe successful. The built-in viewer may make its internal content inaccessible to page DOM; save real WebDriver screenshots and inspect them, and inspect its frame/embedded viewer where the driver exposes it.

For HTTP/HTTPS isolation under Edge WebDriver, pass proxy switches through `ms:edgeOptions.webviewOptions.additionalBrowserArguments`, a list of strings. Microsoft's [capabilities reference](https://learn.microsoft.com/en-us/microsoft-edge/webdriver/capabilities-edge-options#webviewoptions-object) identifies this as the browser-process argument list; `ms:edgeOptions.args` instead goes to the WebView2 host executable. An actual first probe showed the driver replaced the inherited `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS` value with its own flags, and external navigation succeeded. The runner therefore supplies the documented capability, requires a real `ERR_PROXY_CONNECTION_FAILED` remote navigation, checks actual browser process switches and then returns to the embedded app. The isolation applies to WebView2 HTTP/HTTPS only, with explicit local-resource bypasses; it does not disable native sockets or system applications.
