## 已收敛的操作流程

以下描述接入完成后的预期操作，是本项目的适配方案，不是已经存在的可用命令或官方模板开箱行为。

1. **准备并确认工单。** 等独立技术聊天收尾，读取最新规格、技术方案与 ADR，整理本地 Markdown 实施工单。每张说明范围、依赖和可验证的完成条件，由用户确认本次要交给 Agent 的一批。
2. **一次启动整批。** 未来提供统一启动入口，在当前 Windows 电脑上选择本次工单及可调整的四小时默认窗口。启动前检查仓库基线、执行工具、沙箱、必要测试服务与验证命令；缺失条件按影响范围记录并暂停相应工作。
3. **自动调度实施。** 首次先顺序验证完整闭环，稳定后并行处理独立且满足依赖的工单。每张使用独立分支与工作区；一个调度者统一领取和记账，工作者回传自己的结果。共享接口、迁移或测试资源冲突的工作按顺序处理。
4. **自动检查、审查、返修与整合。** 编码 Agent 完成实施，审查 Agent 检查变更，检查失败或存在可修复问题时最多三轮返修。按工单完成必要检查；涉及 Windows 桌面结果时，在真实 Windows 环境验证对应提交。整合进入队列，针对最新目标分支形成候选结果，检查通过后自动合入约定主线；具体实现由工程方案确定，不要求用户逐张手动确认合并。
5. **局部暂停并保留结果。** 必须由用户决定的问题、三轮后仍未通过或无法完成要求的验收，暂停受影响工单及其依赖项，其他明确、独立工单继续。达到时间窗口后停止领取新任务并受控收尾，保留提交、检查和问题记录；不把未完成或未验证任务记为完成。
6. **回来查看结果并续跑。** 输出本批已完成并合并、受阻待回答、到时未完成的清单，附提交、检查/审查证据和待回答问题。用户查看应用与记录、回答必要问题；下次明确启动时先核对保留分支、当前提交及证据再续跑。新增工单另列下一批。

用户日常参与点：确认工单与批次、启动一次运行、回来查看结果并回答真正需要其判断的问题。具体库、字段和脚本组织由工程侧形成方案。

全局工具安装与官方配置骨架已按后续授权完成。完整运行前仍需准备工程/Git 基线、项目检查和测试依赖、本地工单适配、项目入口依赖解析、Codex 与沙箱的实际兼容及 Windows 验收连接。应用实施工单继续等独立技术聊天收尾后再推进。

## 开场说明：接到现有开发流程哪里

Sandcastle 可以理解为安排编码 Agent 连续工作的调度层。Codex 等代理执行具体编码任务；沙箱提供受控执行环境；Sandcastle 通过编排脚本连接运行、检查、审查、返修与分支处理。

建议讨论的接入位置：

> 人与 Agent 对齐规格 → 整理并确认实施工单 → Sandcastle 调用 Codex 执行 implement 的工作 → 自动检查与审查 → 按已定规则返修或停下 → 输出供人检查的改动及验收证据。

这条流程是本项目的候选方案，不是官方开箱保证。任务选择、完成标准、停止条件、是否合并及 Windows 验收如何承接，仍须本次讨论确定并在后续试运行验证。

## 第一轮：先确定实际委托目标

### Q1：最希望 Sandcastle 替你承担什么工作？

代理推荐：起步先顺序自动跑完整批；某张受阻时仍按 D09 跳过，继续下一张独立且明确的工单。先验证环境、验收与自动合并的完整路径，再逐步开放独立工单的有限并行。理由是首次接入的主要不确定性在流程可靠性，顺序运行便于定位失败来源，也减少共享接口变化引起的返工。这是本项目建议，不是官方要求必须顺序。

1. **官方支持并推荐一种无人值守自动合并策略。** 分支文档将 `merge-to-head` 列为适合自动化、CI 和无人值守的策略：临时分支工作完成后自动合回调用时的当前分支。它不是所有 provider 的实际默认；Docker 等 bind-mount 默认是直接在当前工作区执行的 `head`。指定 `branch` 则保留明确的命名分支，适合后续 PR。上述操作是本地 Git 行为，不等于自动创建、推送或合并 GitHub PR。[固定版本分支文档](https://github.com/mattpocock/sandcastle/blob/ed8e7164e0a5d65a0a98c6917508b45cd2de89a8/docs/guide/branch-strategies.md)

2. **模板做法并不统一。** `sequential-reviewer` 每张工单建独立分支，实施后交第二个代理审查，但当前入口没有显式合并或 PR 步骤；实施提示还在审查前关闭工单。`parallel-planner-with-review` 则在分支实施和审查后，调用专门的合并代理，合回当前分支，并在合并提示中关闭相应工单。不能把“选了顺序审查模板”写成“已经自动合并”。[顺序入口](https://github.com/mattpocock/sandcastle/blob/ed8e7164e0a5d65a0a98c6917508b45cd2de89a8/src/templates/sequential-reviewer/main.mts)、[顺序实施提示](https://github.com/mattpocock/sandcastle/blob/ed8e7164e0a5d65a0a98c6917508b45cd2de89a8/src/templates/sequential-reviewer/implement-prompt.md)、[并行审查入口](https://github.com/mattpocock/sandcastle/blob/ed8e7164e0a5d65a0a98c6917508b45cd2de89a8/src/templates/parallel-planner-with-review/main.mts)

3. **模板中的执行结束不等于验收通过。** 并行入口排除抛异常的管线，再选择领先当前分支的结果进行合并；没有解析结构化的审查批准。审查仅运行一轮，可直接修改并提交，也可不修改后输出完成信号。模板让代理跑检查，但入口没有将测试退出码作为合并前的独立硬门槛；也没有检查是否因耗尽轮数而未完成。[并行审查入口](https://github.com/mattpocock/sandcastle/blob/ed8e7164e0a5d65a0a98c6917508b45cd2de89a8/src/templates/parallel-planner-with-review/main.mts)、[审查提示](https://github.com/mattpocock/sandcastle/blob/ed8e7164e0a5d65a0a98c6917508b45cd2de89a8/src/templates/sequential-reviewer/review-prompt.md)、[迭代文档](https://github.com/mattpocock/sandcastle/blob/ed8e7164e0a5d65a0a98c6917508b45cd2de89a8/docs/guide/iterations.md)

4. **冲突处理有两条不同路径。** 库的 `merge-to-head` 合并失败时会中止合并、保留有提交的临时分支，当前 HEAD 不变。并行模板的合并提示则要求代理理解双方改动并解冲突，跑类型检查和测试，失败时先修；当前入口没有额外的结构化“哪些分支失败或跳过”门槛。二者不能混为一个保证。[分支文档](https://github.com/mattpocock/sandcastle/blob/ed8e7164e0a5d65a0a98c6917508b45cd2de89a8/docs/guide/branch-strategies.md)、[合并提示](https://github.com/mattpocock/sandcastle/blob/ed8e7164e0a5d65a0a98c6917508b45cd2de89a8/src/templates/parallel-planner-with-review/merge-prompt.md)

5. **官方已有供编排层执行真正检查的能力。** `run.md` 示例用 `sandbox.exec()` 执行测试，并检查返回的非零退出码后显式抛错。该能力可用于项目的合并门槛；不会因为采用默认模板就自动具备。[运行文档中的检查示例](https://github.com/mattpocock/sandcastle/blob/ed8e7164e0a5d65a0a98c6917508b45cd2de89a8/docs/guide/run.md#createsandbox--reusable-sandbox)

**对 Noterion 的工程适配建议，后续按 D15 承接并验证：** 尊重用户自动合并偏好，独立分支实施和审查后，编排层核验要求的检查并按队列整合到约定本地主线；检查证据对应当前候选提交，不以旧基线的通过结果放行新整合。合并结果、检查证据、受阻原因分别记录；需要用户决定时按 D09 暂停，不将完成信号、有提交或管线正常返回单独当作验收通过。Windows 完整桌面验收仍按正式规格安排，不能由模板默认的 npm 命令替代。上述是本项目适配方案，不是声称官方已经实现的统一最佳实践；推送、GitHub PR 及远端合并不因本地自动合并而自动具备。
