# Noterion：个人知识图谱正式规格

Status: ready-for-agent

更新日期：2026-11-07（Asia/Shanghai）。

本文由已结束的业务 Grill、领域词汇表和已接受的技术决策整理而成。用户已确认本文采用的测试验收边界。已确认范围可据此拆解实施工单；涉及待定选择的工作应先解决对应依赖。本次规格整理不包含应用实现、环境安装或数据库部署。

## Problem Statement

用户在观看视频、阅读网页和书籍时学习了大量知识，但日后遇到实际问题，往往只能记住大致主题，无法迅速回想具体操作，也不容易找到当时的学习资料。

用户希望这个系统成为自己的“外置大脑”：把已经学过的知识和个人理解长期保存在自身记忆之外，在需要时根据线索找回，并重新用于实际问题。

例如，用户需要进入 Docker 容器终端，却忘记了 docker exec 命令。用户希望根据记得的名称或描述词语找到相应知识点，查看自己保存的说明，并能直接打开当时的视频或文档。

用户现有的学习笔记可能十分精简：开头是视频链接，下面只有“MySQL 锁”等主题或要点。这些笔记适合组织知识和资料之间的联系；完整视频、PDF 或书籍则主要作为可回看的学习资料。系统应长期保存这些联系，形成用户能够持续整理、检索和使用的个人知识图谱。

## Solution

### 项目名称与命名寓意

项目名称为 **Noterion**，用户于 2026-11-07 从英文候选名称中选择确认。建议的 GitHub 仓库短名为 **noterion**。

Noterion 是为本项目创作的英文名称，命名灵感来自 **Note**（笔记、学习记录）与 **Orion**（猎户座）。名称经过融合形成，表达的是笔记与星座相结合的意象。

它的寓意是：分散的知识点如同星点，用户的理解及知识之间的联系使它们形成可以辨认、可以循线查找的知识结构；资料关联则保留通往学习来源的线索。随着学习持续积累，这份结构逐渐成为属于用户自己的知识图谱。“星图”在这里承载命名寓意，功能定义继续使用知识点、所属主题与资料关联等领域术语。

### 个人外置大脑的产品愿景

Noterion 的产品定位是 **个人的外置大脑**。这一定位源于用户希望建立“真正属于自己的大脑图谱”的想法：平时学习很多内容，时间久了会忘记细节，希望将已经学过的知识、自己的理解及相关资料联系长期保存在自身记忆之外，在需要时重新调用。

Noterion 长期保存用户整理的知识点、个人理解及其与学习资料之间的联系，让用户依据名称或描述中的线索找回学过的知识，并在实际问题中重新使用。知识图谱组织知识，搜索、描述和资料入口共同支持知识的找回、理解与使用。

这一定位对应三个已有的核心需求：

- **记下来**：持续积累知识点、自己的说明及学习来源，形成长期保留的个人知识结构。
- **找回来**：忘记具体名称或操作时，仍能依据名称或描述中的线索定位知识点。
- **用起来**：找到知识点后，能够阅读完整描述或打开关联资料，帮助处理当前问题。

提供以个人使用为中心的本地桌面应用，正式支持 Windows。开源后，其他使用者各自部署和管理自己的数据。

系统围绕“知识点、描述、所属主题、学习资料和资料关联”组织信息。主题、概念、方法和具体操作都可以成为知识点；主题本身也是知识点。一个知识点可以属于多个主题，始终共用同一节点及其描述、资料关联。当前知识点之间只采用“所属主题”关系。

用户输入名称或描述中记得的词语，搜索结果显示知识点名称和简短描述摘要。选择结果后，应用在图谱中定位并突出该知识点，同时展示完整描述和学习资料入口。用户可以阅读说明、打开资料，或沿所属主题继续浏览。

解释、命令、步骤和个人理解保存为知识点的 description 属性。上传的资料文件由系统长期保存；链接资料保存外部地址。原始资料不默认进行全文解析或知识抽取。基础搜索独立于 AI 可用，DeepSeek 辅助搜索与问答保留为产品方向。

知识构建从显式结构和简单规则开始，支持人工修正。用户通过图谱明确执行删除；共享节点和关联文件按本文规则保留，不提供回收站或删除后恢复。

## User Stories

### 已确认的核心使用需求

1. 作为个人学习者，我希望系统成为自己的外置大脑，长期保存学过的知识点、个人理解及其与资料的联系，以便遇到问题时重新找到和使用这些知识。
2. 作为个人学习者，我希望主题、概念、方法和具体操作都能成为知识点，以便既记录“Docker”这样的主题，也记录“进入容器终端”这样的操作。
3. 作为个人学习者，我希望不同学习记录可以引用同一个知识点，以便持续补充已有知识。
4. 作为个人学习者，我希望同一个知识点可以属于多个主题并共用一个节点，以便从不同主题进入同一份知识。
5. 作为个人学习者，我希望先用“所属主题”关系组织知识点，以便从简单、明确的组织方式开始。
6. 作为个人学习者，我希望为知识点保存描述、命令、步骤和个人理解，以便找到知识点后直接阅读自己留下的说明。
7. 作为个人学习者，我希望知识点可以只有高度凝练的名称或要点，以便尚未写出完整解释时也能组织它和相关资料。
8. 作为个人学习者，我希望不同名称的知识点分别保存，以便系统按我提供的显式内容组织知识。
9. 作为个人学习者，我希望含义不同的同名知识点分别保留，以便区分 MySQL 的“锁”和并发编程的“锁”等不同知识。
10. 作为个人学习者，我希望在系统内修正知识点及所属主题关系，以便持续整理图谱。
11. 作为知识使用者，我希望按知识点名称搜索，以便快速找到记得名称的知识。
12. 作为知识使用者，我希望按描述中的词语搜索，以便忘记知识点名称时也能找到相关说明。
13. 作为知识使用者，我希望搜索结果显示名称和简短描述摘要，以便判断哪个结果与当前问题有关。
14. 作为知识使用者，我希望点击搜索结果后在图谱中定位并突出对应节点，以便知道这份知识在图谱中的位置。
15. 作为知识使用者，我希望选择知识点时同时看到完整描述和资料入口，以便立即阅读说明或继续回看资料。
16. 作为知识使用者，我希望沿“所属主题”关系浏览，以便继续查看相关主题及其下属知识点。
17. 作为知识使用者，我希望主图默认展示知识点，需要时再查看关联资料，以便围绕知识结构浏览。
18. 作为个人学习者，我希望上传的学习资料保存在系统内，以便以后仍能打开对应文件。
19. 作为个人学习者，我希望通过外部链接关联视频或网页，以便保留知识点与线上来源之间的联系。
20. 作为个人学习者，我希望一个知识点能关联多份资料，同一份资料也能关联多个知识点，以便复用已有来源。
21. 作为知识使用者，我希望从知识点打开相关文件或链接，以便阅读具体内容。
22. 作为个人学习者，我希望删除知识点时保留上传的资料文件，以便资料不因图谱整理而丢失。
23. 作为个人学习者，我希望保存的数据在关闭并重新打开应用后仍然存在，以便持续积累个人知识。
24. 作为图谱维护者，我希望通过图谱中的明确操作删除节点，以便由自己决定移除哪些知识。
25. 作为图谱维护者，我希望删除主题时仍保留属于其他保留主题的共享知识点，以便其他主题下的知识不被误删。
26. 作为图谱维护者，我希望删除主题时，一并移除因本次删除而失去全部所属主题的受影响下属知识点，以便清理本次移除的主题结构。
27. 作为图谱维护者，我希望独立知识点不被全局自动清理，以便保留自己仍需要的知识。
28. 作为图谱维护者，我希望明确删除后直接移除知识点，不进入回收站，以便按自己执行的删除操作整理图谱。
29. 作为图谱维护者，我希望描述随知识点一起保存、修改和删除，以便知识点的说明与节点保持一致。
30. 作为 Windows 使用者，我希望在个人电脑上使用本地桌面应用，以便管理自己的知识和资料。
31. 作为开源项目使用者，我希望各自部署并管理自己的数据，以便独立使用个人知识图谱。
32. 作为知识使用者，我希望不接入 AI 也能搜索和定位知识点，以便基础查找功能独立可用。
33. 作为图谱维护者，我希望只维护一次正式知识，图查询表示由系统维护并可从正式数据重建，以便不必手工维护两份相同知识。

### 已记录的输入约束与产品方向

以下故事保留此前已表达的需求和约束；导入细节、AI 行为及相关交付安排尚未完整定义，不据此直接承诺未讨论的实现。

34. 作为个人学习者，我希望继续在系统外编写笔记，并使用 Markdown 或 CSV 这样的结构化输入，以便沿用自己的学习记录方式。
35. 作为个人学习者，我希望系统提供约定的输入结构，将标题、条目和解释分别组织为知识点、所属主题和描述，并支持预览及修正整理结果，以便按明确规则生成图谱。
36. 作为个人学习者，我希望输入开头指定的默认来源关联其中的知识点，以便保留原始学习来源。
37. 作为个人学习者，我希望成功入图后不必在系统内长期保存结构化输入文件副本，以便由自己在外部管理笔记文件。
38. 作为个人学习者，我希望明确属于原记录修改的输入更新对应导入记录，完全重复的输入提示已存在，以便识别重复提交和后续补充。
39. 作为图谱维护者，我希望输入文件中省略条目时保留已有节点和关联，以便文件内容减少不会代替自己执行图谱删除。
40. 作为知识使用者，我希望将来通过 DeepSeek 辅助搜索和问答，并允许补充通用知识，以便更方便地解决实际问题。
41. 作为个人学习者，我希望将来能够选择是否读取原始资料内容来辅助搜索，以便根据需要使用额外的内容检索能力。

## Implementation Decisions

### 领域模型与知识组织

- **知识点**是图谱中可以单独定位的对象，名称用于展示和搜索，description 保存解释、命令、步骤和个人理解。
- **主题**是作为组织入口的知识点。本项目不因主题不同而把同一知识点复制到互不相干的图中。
- **所属主题**连接知识点与主题；一个知识点可以有多个所属主题，仍保持同一节点身份。
- **资料关联**连接知识点与学习资料，支持一个知识点关联多份资料，也支持同一资料供多个知识点引用。资料关联与知识点之间的“所属主题”关系分别处理。
- description 属于知识点属性，不建立独立解释资料或解释节点。
- 不同名称按不同知识点处理；不进行同义识别、改名推断或跨名称智能归并。同名异义可以分别存在，不能仅凭名称相同就强制复用；具体显式标识机制尚待设计。
- 支持用户在应用内修正知识点及其关系；具体编辑布局与操作控件由后续设计细化。

### 搜索与查看

- 基础检索覆盖知识点名称和 description；查询词仅出现在描述中时，也应返回对应知识点。
- 搜索结果以知识点为单位，显示名称及简短描述摘要。
- 点击结果后的正常流程必须包含图谱定位和突出显示，同时展示完整描述及关联资料入口。
- 主图默认显示知识点；关联资料可通过节点详情查看，需要时展开。具体画布布局、呈现样式和展开交互尚未确定。
- 主题本身作为知识点，适用相同的检索、描述和资料关联规则。
- 搜索支持名称和 description 的片段包含匹配；多个关键词由最终使用者选择全部匹配（all）或任意匹配（any）。具体排序、摘要生成及索引由工程设计落实，不推导语义搜索、独立分词服务或 AI 搜索为基础能力。
- 原始视频、PDF、书籍等可以仅作为资料关联，不默认抽取其内容、节点或关系。

### 资料与保存

- 文件资料的本体由可配置对象存储服务长期保存，支持本地自部署或云端配置；PostgreSQL 保存正式资料信息、就绪状态与稳定存储引用。具体产品和真实连接配置在实施时验证，不自动创建云资源或迁移文件。
- 文件包括 PDF、图片、文档和本地视频；单视频 1—2 GB 是真实使用场景，不是容量上限。保存副本主要用于查看，不要求外部编辑、自由改名移动或变更跟踪。
- PDF、图片和支持的视频默认在应用内只读查看，其他格式或失败时提供外部打开；需要本机路径时使用受控查看缓存。大视频验证按需读取与拖动播放，不承诺全部编码或自动转码。
- 文件本体与正式资料记录均就绪后，才能表示该文件已保存可打开；未完成上传不能仅因已有 PostgreSQL 记录而显示成功。
- 链接资料保存外部地址及关联；链接失效后不承担原站内容归档或恢复要求。
- 删除知识点或主题不连带删除上传的资料文件。
- description 随节点状态变化，不能作为独立文件资料处理。
- 用户起步时十几篇学习记录只是初始使用量，不是容量上限或性能验收指标。

### 删除

| 情况 | 已确认行为 |
| --- | --- |
| 用户希望删除节点 | 通过图谱中的明确操作执行 |
| 删除某个主题，其下属知识点仍属于其他保留主题 | 保留共享知识点，只移除与本次被删主题的所属连接 |
| 本次主题删除使受影响下属知识点失去全部所属主题 | 随本次主题删除级联移除 |
| 原本独立、未归入主题的知识点 | 不因上述规则进行全局扫描和自动删除 |
| 节点被删除 | 直接移除知识点及其 description，不提供回收站或删除后恢复 |
| 删除涉及上传资料的知识点 | 资料文件保留 |
| 输入文件比之前少了条目 | 不触发已有节点或关联的删除 |

- 回收站和删除后恢复已由用户从当前范围移除，不再作为实施依赖。为可靠同步所需的技术删除记录不能被实现为未要求的用户回收站。
- 主题删除引起的级联规则不自动推广到普通解除所属关系等其他操作。
- 删除以应用业务规则为准，不能直接采用数据库默认级联来替代这些规则。

### 已确认的技术约束

| 项目 | 决定及边界 |
| --- | --- |
| 桌面框架 | 采用 Tauri，Rust 本地核心与 WebView 界面通过明确接口交互 |
| 支持平台 | 正式支持从 Windows 开始；未来其他桌面系统需分别打包和验证 |
| PostgreSQL | 保存完整正式结构化业务事实，包括知识点、description、知识关系、资料信息与关联，以及必要导入记录和图同步待办 |
| Neo4j | 提供由正式事实生成、可重建的图查询副本，承担实际图查询 |
| 业务修改入口 | 应用对正式事实的修改以 PostgreSQL 为准；Neo4j 不保存无法从正式记录重建的独有业务事实 |
| 文件本体 | 采用可配置对象存储，支持本地或云端配置；具体服务产品与兼容性由工程验证 |
| 正式保存与图更新 | PostgreSQL 提交即确认保存；图更新单独显示状态，未赶上的图不能伪装成最新 |
| Neo4j 故障 | 其他必要组件正常时继续保存、基础搜索、阅读和资料访问；图功能明确不可用，副本赶上正式变化后恢复 |
| 同步任务生命周期 | 在 Tauri/Rust 桌面应用内运行；完全退出后暂停，待办持久保留在 PostgreSQL，下次启动续处理 |
| 数据库运行 | 用户本人接受安装、账号及连接配置，也接受通过 Docker 部署数据库 |
| 普通开源使用者的交付 | 标准安装和运行方式尚未确定，不能将个人接受 Docker 等同于所有使用者的要求 |

- Tauri、数据库权威职责与对象存储分别遵循已接受的 ADR 0001、ADR 0002 和 ADR 0003；删除范围以本文最新用户更正为准。
- 工程推荐基线为 React/TypeScript/Vite、Cytoscape.js、SQLx、Neo4j HTTP Query API 与 Rust S3 SDK；这些是受委托形成的工程方案，不表述为用户逐库指定。兼容版本、具体数据结构和接口在实施时落实与验证。
- 图副本同步需要由应用设计，不能认为 Docker 或两个数据库会自动共同提交。
- PostgreSQL 同事务待投递记录与应用内投影任务是工程推荐；持久待办、幂等、顺序检查、重试及重建协调由工程设计落实，不增加独立常驻同步服务或消息集群。
- 图刷新和同步时限尚无数值承诺；工程实现须遵守已确认的保存、独立状态和故障行为，不能把图查询失败显示成不存在或无关联。

### 建议的职责划分

以下是根据已确认流程整理的模块职责，用于后续设计与工单拆解；不指定代码结构或新增服务：

| 职责 | 对外能力 |
| --- | --- |
| 知识组织 | 保存和修正知识点、description 与所属主题，执行共享节点保留规则 |
| 检索与图谱查看 | 搜索名称和描述，返回摘要，定位节点并查看所属结构 |
| 资料管理 | 保存文件资料与链接资料，维护资料关联，提供打开入口 |
| 删除 | 按业务规则直接删除、保留共享知识点及文件，不提供回收站或恢复 |
| 持久化与图查询副本 | 维护 PostgreSQL 正式数据，供 Neo4j 图查询表示同步与重建使用 |
| 桌面交互 | 将搜索、图谱、描述和资料入口组成连续的使用流程 |

这些职责通过同一桌面应用协作。无需因职责分组就分别部署服务或引入消息中间件。具体接口契约在对应实施设计中确定。

### 暂缓细化的输入规则

此前确认的约束继续有效：

- 输入格式偏好为 Markdown 和 CSV，具体结构由系统提供模板。
- 标题和条目可按约定形成知识点与所属主题；解释进入 description。
- 支持预览整理结果并进行修正，具体交互随输入契约设计细化。
- 文首默认来源关联整份输入中的知识点。
- 成功入图后无需长期保留结构化输入文件的系统内副本。
- 保留支持更新原记录及精确重复提示所需的必要导入记录；明确的原记录修改更新对应导入记录，完全重复输入提示已存在。
- 导入对图谱只做新增补充；输入缺少条目不撤回或删除已有节点或关联。
- 不增加对已维护名称的智能推断。
- 上述约束不等于已确定完整模板语法、身份匹配方式、字段覆盖策略、导出格式或备份恢复方案。

## Testing Decisions

### 用户已确认的测试边界

主要以桌面应用的完整用户操作作为验收边界，验证搜索、图谱定位、描述、资料和删除之间的外部行为。持久化与图副本重建也通过重启、重建后可观察到的业务结果验证。用户在拆工单时移除了回收站，因此删除后恢复不再属于验收范围。

“外置大脑”定位通过这些已有场景检验：积累的知识能够长期保留，用户能够根据线索找回，并能通过描述或原始资料重新使用。

优先复用这一个应用级边界，不为每个内部模块分别建立一套耦合其实现的验收接口。后续如遇桌面自动化无法稳定覆盖的高风险业务规则，可在同一应用操作接口补充必要集成测试；这属于测试实现选择，不改变已确认的用户结果。

好测试应验证用户能做什么、操作后的知识和资料是什么状态，以及错误是否如实反映；不绑定组件层级、数据库表名、内部函数调用顺序、图布局坐标或测试用例与实现逐句对应。

### 核心验收场景

| 编号 | 场景和预期结果 | 对应用户故事 |
| --- | --- | --- |
| T01 | 准备“进入容器终端”知识点，description 中包含 docker exec；搜索仅出现在描述中的词语仍返回该点及名称、摘要；选择后在图谱定位并突出节点，同时显示完整描述与资料入口 | 6、12—15 |
| T02 | 按知识点名称搜索能返回对应知识点；主题节点也可搜索和查看自己的描述及资料 | 2、11、13—16 |
| T03 | 一个知识点属于两个主题；从两个主题访问时均指向同一知识点及同一份描述、资料关联；不产生重复知识点 | 3—4、16、20 |
| T04 | 修改一个共享知识点后，从不同所属主题访问时看到相同的正式内容；不同名称及明确不同含义的知识点不会被自动归并 | 8—10 |
| T05 | 一个知识点关联文件和外部链接，同一资料关联多个知识点；文件从对象存储读取，按默认只读查看或外部打开路径访问，链接打开外部地址；不要求默认解析资料全文 | 18—21 |
| T06 | 删除主题：仍属于其他保留主题的共享知识点保留，并断开本次所属连接；因本次删除而失去全部所属主题的受影响下属节点移除；独立知识点保持；相关上传文件仍存在 | 22、24—27 |
| T07 | 在图谱明确删除知识点后，搜索、详情和赶上同步的图中均不再出现该点及其 description；重启和重建不使其复活；不提供回收站或恢复，关联资料文件仍保留 | 22、24、28—29 |
| T08 | 保存知识点、描述、所属主题、资料关联和上传文件，关闭后重新打开应用，仍能通过相同查找流程访问这些数据及文件 | 1、18、23 |
| T09 | 以 PostgreSQL 中的正式事实重建 Neo4j 图查询副本，完成后从应用观察到的节点身份和所属主题与正式数据一致；描述与资料入口仍对应同一知识点；不要求用户再次录入 | 33 |
| T10 | 未配置 DeepSeek 时，搜索、图谱定位、描述查看和资料入口仍可完成核心使用流程 | 11—21、32 |
| T11 | Neo4j 不可用时，其他所需组件正常仍能保存、搜索和查看正式数据及打开资料；界面明确图不可用。退出后重启，待办继续处理，图赶上正式变化后恢复；不因重试产生重复节点或旧数据回退 | 23、33；技术 Q14、Q15、Q22 |
| T12 | 按名称或 description 的片段可查到知识点，单字、短中文词与包含特殊字符的输入保持匹配正确；多词 all/any 由使用者选择并产生相应结果 | 11—13；技术 Q20、Q21 |
| T13 | 上传并重新打开 1—2 GB 实际视频样本，支持的编码可按需读取和拖动播放，失败可外部打开；上传或资料记录未完成时不显示已就绪，不把全部字节一次性送入前端内存 | 18、21、23；技术 Q16—Q19 |

### 覆盖对象、先例与未决测试

- 通过上述应用级场景覆盖知识组织、检索与图谱查看、资料管理、删除、持久化及图副本重建，重点验证它们协作后的行为。
- 当前仓库只有规格、领域文档和研究资料，没有应用代码、现有测试框架或可复用测试先例。具体桌面自动化工具、测试数据准备方式和运行命令将在实现设计时确定。
- 导入结果预览与修正、精确重复、已知原记录更新和缺少条目不删除等测试，待导入契约细化后补齐；这些已知约束应保持。
- 保存与图同步时机、服务故障及恢复后的界面行为按 Q14、Q15、Q22 验证；具体自动化方案由工程落实。
- 搜索排序、容量、响应时限和图渲染规模没有已确认数值，不编造性能门槛；中文片段包含与 all/any 按已确认规则验证。
- AI 回答、通用知识补充及可选资料读取的测试，待其产品行为和外发范围明确后制定。

## Out of Scope

以下不属于本规格的已定义交付范围，或已被明确暂缓：

- NAS 部署目标：已由更晚的技术讨论取消。
- 手机端、跨设备同步和多人协作。
- 专门的离线模式或离线安装验收；这不要求本地操作必须联网。
- 完整笔记编辑器：当前笔记在系统外编写。
- 熟悉程度、陌生区域、重点区域等学习状态呈现。
- 扩充“所属主题”以外的知识点关系类型。
- 自动同义合并、跨名称智能归并、自动改名识别和语义消歧算法。
- 默认读取全部原始视频、网页、PDF 或书籍并抽取知识关系。
- 失效链接的内容归档及恢复。
- 自动清理全部没有主题的独立节点，或因节点删除自动清理上传文件。
- 回收站和删除后恢复：用户在工单拆分时明确移除。
- 完整导入导出格式、交换包、备份与恢复方案的细化。
- 重新划分 MVP、版本排期或把未决 AI 需求默认为已排期功能。
- 未经确定的资料外发、额外云端存储要求，以及直接安装依赖、启动数据库或创建应用实现。
