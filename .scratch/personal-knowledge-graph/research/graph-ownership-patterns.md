# PG＋Neo4j：什么时候选查询投影，什么时候按事实分工

核验日期：2026-11-07（Asia/Shanghai）。应用 research 技能，仅采用微软、AWS、Neo4j 的官方架构与数据库资料。本报告针对“是否需要把同样的数据维护两遍”的疑问比较成熟模式，未将 A 或 B 当作用户已确认决定；未实施数据库或修改其他项目文档。

后续决定（同日）：用户已在比较后明确选择 A，理由是需求仍在细化，希望完整正式事实集中在 PostgreSQL，Neo4j 为可重建查询副本。本文保留选择前的条件研究；最新决定见 [ADR 0002](../../../docs/adr/0002-postgresql-source-neo4j-projection.md)。图更新时效和故障行为仍未确认。

## 1. 两条路线都不应要求用户手工维护两份相同知识

| 路线 | 同一个知识点、描述和所属关系，谁有最终决定权 | 另一库是什么 | 用户如何操作 |
| --- | --- | --- | --- |
| **A：PG 事实源＋Neo4j 可重建图投影** | PostgreSQL | Neo4j 中的相关内容是程序自动派生的查询副本 | 在应用里修改一次，由程序更新图副本 |
| **B：Neo4j 权威图＋PG 权威其他数据** | Neo4j；PG 只权威保存划给它的其他事实 | 两库保存不同职责的数据，必要时有引用或派生缓存 | 在应用里修改一次，由相应模块写负责的库 |
| **同一事实双主，不是此处的 B** | PG 和 Neo4j 都能独立修改同一知识点、描述或关系 | 两边都声称自己正确 | 必须额外解决冲突、覆盖顺序和双向同步，不能默默要求用户自行对齐 |

**A 是自动复制一种查询表示；B 是不同数据各有一个负责人。** 两者都可能涉及同步或跨库调用，但这不等于“同一条业务信息要手工保存两遍”。物理上出现同一个标识或缓存名称，也不等于出现两个权威来源。关键是发生不一致时究竟以哪一边为准。

## 2. 官方资料支持的是有条件的模式

微软的 Materialized View 模式把投影定义为从源数据生成的查询表示：查询方将其视为只读，专门组件负责更新，内容可以从源数据重新构建。这与 A 的职责划分相符；它是架构概念，不要求使用某个引擎自带的 materialized-view 对象。[Microsoft Materialized View](https://learn.microsoft.com/en-us/azure/architecture/patterns/materialized-view)。

微软 CQRS 支持将读模型与写模型分开，并讨论异步读副本的一致性成本；同一页面也明确指出，领域和规则简单、普通 CRUD 足够时，CQRS 可能不合适。因此不能把“读写分离＋双库投影”包装成任何项目都应采用的高级默认值；CQRS 也不天然要求事件溯源或两个数据库。[Microsoft CQRS](https://learn.microsoft.com/en-us/azure/architecture/patterns/cqrs)。

AWS 的 Database-per-service 模式强调按业务需要选择数据存储、明确数据访问边界，这能为 B 的“不同事实归不同 owner”提供依据。原文针对微服务，本项目借鉴数据所有权原则而非照搬部署形式：这些职责可以仍在同一个 Tauri/Rust 应用的不同模块中实现。**不需要为了选 B 就新增微服务、网关或云平台。** 后一句是本项目推断。[AWS Database-per-service](https://docs.aws.amazon.com/prescriptive-guidance/latest/modernization-data-persistence/database-per-service.html)。

Neo4j 是具有原生图模型和事务能力的数据库，能够承担图写模型；它的角色不限于给 PG 作缓存。图操作可以在一个 Neo4j 事务里共同提交或回滚，但不会自动涵盖另一引擎的写入。[Neo4j native graph](https://neo4j.com/docs/getting-started/whats-neo4j/)、[Neo4j transactions](https://neo4j.com/docs/operations-manual/current/database-internals/transaction-management/)。

这些官方资料描述适用条件与代价，并没有得出“PG＋Neo4j 只有 A 才是行业最佳实践”的结论。本文也没有调查企业采用比例，不能用“多数公司都这样”支撑选择。

## 3. 条件矩阵

以下是将官方模式应用到本项目时的设计判断，不是性能评测，也不是用户已确认偏好。

| 判断条件 | 更支持 A：PG 事实源、Neo4j 查询投影 | 更支持 B：各类事实独立权威保存 |
| --- | --- | --- |
| 引入 Neo4j 的目的 | 在已有业务数据上增加图查询、路径探索或读优化 | 图本身就是日常创建、修改和校验的主要业务模型 |
| 核心写操作在哪里判断 | 应用先围绕 PG 中的完整事实判断，再生成图表示 | 知识点、描述、主题关系及图生命周期规则主要在图模型内判断 |
| 已有系统基础 | 已有 PG 业务系统，复杂写事务和关联状态已经集中于 PG | 没有必须服从的 PG 旧系统，图与其他数据的 owner 边界可以直接设计 |
| 必须原子的操作 | 知识点、关系和其他核心记录经常必须一起在 PG 内提交 | 多条关系变更、共享节点保留及图状态变化应一起在 Neo4j 内提交 |
| Neo4j 中正式数据的修改 | 可以禁止直接修改正式投影，所有修改回到 PG 的业务入口 | 希望通过图写模型正式维护节点与关系，而不先在 PG 复制一份权威图 |
| 图内容能否丢弃重算 | 可以完全从 PG 事实及投影规则重建 | 图中保存独有事实，不能仅从 PG 完整重建 |
| 延迟要求 | 接受图投影可能短暂落后，并愿意定义该状态下的行为 | 图操作直接查询 Neo4j 的已提交结果；跨库关联流程仍需要协调 |
| PG 与图的独立边界 | PG 统一承载业务，Neo4j 主要是另一种读取方式 | PG 有真实独立职责，例如资料目录或其他管理数据；无需复制整套知识点与关系 |
| 愿意维护哪种复杂度 | 自动投影更新、重试、顺序控制与重建 | 跨 owner 引用、部分完成的操作、重试和必要补偿 |
| 学习目标 | 想学习查询投影、数据同步，以及 Cypher 查询 | 想把图数据库作为正式写入系统，学习图建模、图事务和图约束 |

“接受图延迟”不等于“所有页面都可显示旧数据”；A 仍需明确操作后何时查询事实源、何时等待投影。B 也不等于全系统即时一致：跨 Neo4j 与 PG 的流程仍跨两个事务边界。两项均未由用户确认。

## 4. 用反例避免误选

**反例一：把 A 当成两边都能随意修改。** 用户在 PG 修改知识点名称，又在 Neo4j 修改同一名称，并希望两边自动猜测正确结果。这已经越过单向读投影，变成同一事实双主；不能仍声称“Neo4j 随时可从 PG 重建且不丢正式数据”。

**反例二：把 B 当成节点与边也必须在 PG 全存一遍。** 如果知识点、`description`、所属主题关系由 Neo4j 权威保存，PG 只保存其负责的资料信息，则没有必要为了“两个库都用了”就在 PG 再建立一份可独立修改的完整图。其他地方需要知识点标识时，可以引用；如果需要缓存，明确它是派生数据。

**反例三：把 B 的每次图操作都说成跨库事务。** 假设 B 将知识点、主题关系以及相关图删除／回收站状态都放在 Neo4j，并且删除知识点时上传文件本体保留，那么共享知识点判断和图状态变更可以围绕 Neo4j 的事务设计，不必同时修改 PG。这是假设性的边界示例，不是已定 schema。新增资料并将其关联到图时，才可能跨到资料 owner，需要相应流程。

**反例四：只因为是简单产品就搭完整 CQRS 平台。** 若普通查询和维护已经足够，A 仍会增加投影任务、失败重试与滞后状态。微软明确给出简单 CRUD 不一定适合 CQRS 的条件。反过来，用户明确想学习双库和图查询，这本身可以成为承担这些成本的理由，不能以“现在数据不多”否决。

**反例五：把自动同步说成一次网络请求即可可靠完成。** PG 提交后直接写 Neo4j，第二步可能失败；A 需要可靠地记住待同步变化。AWS 的 outbox 模式用于处理业务写入与后续事件发送的双写问题，并要求考虑重复及顺序。它不提供两个数据库的全局事务；借用模式不要求引入 AWS、Kafka 或 CDC。[AWS Transactional Outbox](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)。

## 5. 当前项目适配判断

当前有效模型是知识点及其 `description`，知识点间先支持“所属主题”，允许多主题与共享节点；搜索名称和描述；主题删除保留仍有其他主题的共享知识点，支持回收站。名称不同按不同点处理，不做自动同义或改名推断。导入导出、备份恢复和版本划分暂缓，不在本报告展开。

**当前没有已经实现、必须兼容的 PG 业务系统。** 因此“已有复杂 PG 写事务、加一层图查询”的典型 A 前提，尚不能当作本项目事实。A 的成立理由可以是希望统一核心事实、学习自动派生图和保持一个完整事实入口，但不能仅因为 PG 很通用就默认所有知识关系必须先存 PG。

**B 对当前图操作也有明确适配性。** 多主题、共享删除和图恢复属于图对象之间的维护规则；如果用户希望 Neo4j 是正式知识模型，围绕它保持这些状态是一种连贯选择。PG 应分配真实独立职责；“其他数据”到底有哪些，需进一步明确，不能故意拆开一次必须共同判断的规则，只为把两个库都用上。

**推荐当前的判断顺序：先决定图的所有权，再决定同步。**

- 如果“PG 中的数据是正式记录，Neo4j 帮我更好地查询和探索”符合期望，则 A 合适；程序维护副本，用户不用维护两份。
- 如果“知识点和关系本来就是 Neo4j 里的正式图，PG 管其他数据”更符合期望，则 B 合适；每类事实一个 owner，同样不用手工维护两份。
- 如果“希望两边随便修改相同知识并自动合并”，那是另一项双主与冲突解决需求，不应藏在 A 或 B 名称中。

用户已确认希望使用 PG＋Neo4j，但尚未确认以上哪种权威分工，也尚未接受图同步延迟。本报告保持两条路线开放，不以“统一行业最佳”代替取舍。

## 6. 供技术访谈优先引用的官方页面

1. [Microsoft Materialized View](https://learn.microsoft.com/en-us/azure/architecture/patterns/materialized-view)：解释 A 为什么是可重建、由程序维护的查询投影。
2. [Microsoft CQRS](https://learn.microsoft.com/en-us/azure/architecture/patterns/cqrs)：说明读写模型分工、成本，以及简单 CRUD 可能不适合的条件。
3. [AWS Database-per-service](https://docs.aws.amazon.com/prescriptive-guidance/latest/modernization-data-persistence/database-per-service.html)：借鉴按业务边界选择存储与明确 owner，不照搬微服务部署。
4. [AWS Transactional Outbox](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)：解释自动派生可靠性与重复、顺序问题。
5. [Neo4j transactions](https://neo4j.com/docs/operations-manual/current/database-internals/transaction-management/)：确认图写操作可以在 Neo4j 自身事务中提交或回滚。
