# 本地 S3 兼容对象存储：当前候选状态

核验日期：2026-11-07（Asia/Shanghai）。范围仅为 MinIO 社区项目及一个 RustFS 对照，不决定本项目文件保存类别或具体产品。没有安装软件、拉取镜像、创建账户或运行容器。

项目背景：Tauri/Rust、PostgreSQL 事实源及 Neo4j 图投影路线已确认；作为学习资料上传的文件需要保存本体。本文只提供“若采用自部署对象存储”时的当前事实，不扩展 NAS、分布式部署或备份功能。

## MinIO 社区项目：不能沿用旧发行印象

- 官方 `minio/minio` 仓库显示于 **2026-04-25** 归档，处于只读状态；README 首部明确写明该仓库不再维护。[官方仓库](https://github.com/minio/minio)。
- README 的社区分发说明为 **source-only**：不再提供预编译的社区二进制发行；历史二进制保留供参考，但不再更新。所列使用路径是源码编译，或利用仓库 Dockerfile 自行构建镜像。[官方 README](https://github.com/minio/minio/blob/master/README.md)。
- 核验时 Releases 顶部仍为 `RELEASE.2025-10-15T17-29-55Z`，该发行说明也要求容器使用者克隆源码自行构建。源码和历史版本可访问，不代表仍有持续维护的官方社区发行线。[官方 Releases](https://github.com/minio/minio/releases)。
- README 同时引导至 AIStor 产品线；不能把这些不同产品的分发与维护条件直接写成原 MinIO 社区版的条件。本文没有评估 AIStor 的许可或交付，也不将其扩列为已推荐候选。

**项目判断：** 原社区源码仍可研究和自行构建，归档不等于源代码消失。但在本次新项目选型中，不宜按“持续维护、现成社区镜像可直接作为默认依赖”的旧印象推荐它。README 中残留的源码安装与更新措辞，应结合首部“不再维护”和仓库归档状态理解。

本次未访问镜像仓库的具体镜像清单，也未拉取任何镜像；不声称所有历史镜像都已删除或无法拉取。

## RustFS：保留为有限对照

- 官方仓库当前未归档；核验时 `releases/latest` 指向 **1.0.4**，对应发行页包含维护修复记录。其官网仓库中的公告源文件标注 **2026-09-16** 宣布 1.0.0 GA。这证明存在当前官方发行活动，不是本项目对长期维护或生产成熟度的独立认证。[官方仓库](https://github.com/rustfs/rustfs)、[1.0.4 发行页](https://github.com/rustfs/rustfs/releases/tag/1.0.4)、[GA 公告源码](https://github.com/rustfs/rustfs.com/blob/main/content/blog/2026-09-16-announcing-rustfs-1-0-0-ga/index.mdx)。
- 官方文档提供 `rustfs/rustfs` 镜像、本地 Docker 和 Compose 路径，使用本地持久化卷或主机目录。所核验的本地启动例不涉及创建云存储账户；具体镜像可用性、Windows Docker 挂载与应用读写尚未在本机验证。[官方 Docker 文档源码](https://github.com/rustfs/docs.rustfs.com/blob/main/content/en/installation/container/docker.md)。
- 官方 S3 兼容矩阵明确说明覆盖的是经过测试的 API 子集，并不承诺所有标准或厂商专用行为。矩阵包括常见对象上传、下载、删除、列表和部分分段上传行为，也记录未实现及排除的行为；该页的快照注明核验于 2026-08-09，因此实际采用时要对选定发行版和项目需要的 API 再验证。[官方 S3 兼容矩阵](https://github.com/rustfs/docs.rustfs.com/blob/main/content/en/reference/s3-compatibility.md)。

**项目判断：** RustFS 与用户的 Rust 兴趣相关，可作为本地对象存储的一项候选；语言相同或公布 GA 不构成“比其他产品更成熟”的依据。本轮只记录其存在和发行路径，不强推采用，不复制官网性能或成熟度营销比较。

## 选择类别时需要保持的边界

1. **S3 兼容不等于购买或接入 AWS S3。** 本报告讨论自己运行服务、使用其本地 endpoint；没有创建任何云账户，也没有据此授权外发个人资料。
2. **对象存储也需要底层磁盘保存数据。** 本地卷或主机目录是服务保存本体的位置；不能把对象存储误解成无需管理本机数据位置。
3. **Bucket 是组织对象的逻辑空间，单个 bucket 或单机容器不能据此宣称高可用。** RustFS 官方也明确区分单节点单盘与其他拓扑，并说明某些被接受的拓扑不保证主机故障容忍。本项目没有因此新增多节点要求。[官方部署边界](https://github.com/rustfs/rustfs#quickstart)。
4. **本项目所需 API 与故障处理尚未验证。** 官方文档能证明候选的接口与分发路径；不能替代上传后能打开、错误可解释以及数据库记录与对象对应关系的应用验证。

## 供访谈使用的结论

本轮可以先讨论“应用管理的普通文件目录”与“自部署对象存储服务”这两类保存方式，以及用户是否希望在资源管理器中直接管理文件。具体产品可以在类别确认后再决定。

若用户倾向对象存储，MinIO 原社区项目的归档及 source-only 状态必须纳入判断；RustFS 可继续验证。本报告不据此选择对象存储，也不扩展数据库内二进制、NAS、复制、备份恢复或分布式功能的产品方案。
