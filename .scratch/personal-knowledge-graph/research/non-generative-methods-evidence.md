# 非生成式 AI 知识图谱构建方法：一手资料核验笔记

实际检索日期：2026-11-07（Asia/Shanghai）。范围：为个人知识图谱提供研究输入；以下建议和示例均未获用户批准为实施规则，不修改需求草稿或领域词汇表。

## 结论

本项目首版“找到知识点及相关资料”完全可以由结构化输入、显式资料关联、稳定 ID、人工别名和普通检索完成。确定性转换只需要把已写出的信息转换为节点和边，不需要先从极简文字中推断出丰富语义。标准与技术已有长期先例：SKOS 推荐标准发表于 2009 年，R2RML 发表于 2012 年，CSV 到 RDF 的 W3C 推荐标准发表于 2015 年。它们分别提供概念组织、关系数据映射和表格映射方法，均不以生成式模型为前提。[SKOS Reference](https://www.w3.org/TR/skos-reference/)、[R2RML](https://www.w3.org/TR/r2rml/)、[Generating RDF from Tabular Data](https://www.w3.org/TR/2015/REC-csv2rdf-20151217/)。

对本项目的建议（研究推论）：先验证“一点一页”和“单篇结构笔记确定性映射”两种录入负担；如果需要跨工具迁移或批量整理，再验证 CSV 节点表、关系表和资料关联表。数据库可以先采用普通表；是否使用 RDF 或专门图库，与是否能构建知识图谱是两个选择。

## 可直接复核的事实与方法边界

| 方法 | 官方材料实际支持什么 | 应用于本项目时的边界（研究判断） |
|---|---|---|
| 显式链接与反向索引 | Obsidian 内部链接可指向笔记、附件、标题及块；反向链接列出其他笔记指向当前笔记的链接，未链接提及则是名字出现的索引。[内部链接](https://obsidian.md/help/links)、[Backlinks](https://obsidian.md/help/plugins/backlinks) | `A 链接 B` 可以可靠记录为引用；反向显示不增加一条新的“B 依赖 A”知识事实。链接不自带“前置知识”“原因”等语义。 |
| 标题、列表与结构 | Markdown 是结构化纯文本，CommonMark 定义标题、列表、块和内联结构；其简介记录原始 Markdown 于 2004 年发布。[CommonMark 0.31.2](https://spec.commonmark.org/0.31.2/) | 解析器能确定某条目位于哪个标题下；“位于标题下”首先是笔记结构，不能自动解释成属于、组成、先决条件或操作步骤。需要用户约定。 |
| 标签与结构字段 | Obsidian 标签用于查找和筛选，支持嵌套标签；属性可存储文字、链接、日期、数字等，并以文件顶部 YAML 保存。[Tags](https://obsidian.md/help/tags)、[Properties](https://obsidian.md/help/properties) | `#Docker` 可以是检索分类；`类型: 操作` 可以是字段。二者不自动证明两个知识点间存在某种语义关系。YAML 格式本身也不会决定来源继承。 |
| 概念 ID、首选名和别名 | SKOS 区分 `prefLabel`、`altLabel`、`hiddenLabel`，后者可支持拼写变体检索；概念可以有独立 URI。[SKOS §5](https://www.w3.org/TR/skos-reference/#labels) | 稳定 ID 与显示名称分离，维护一个小词典即可把“容器终端”等入口映射至已存在知识点。同名不是同一概念的充分条件，别名需要按语境维护。 |
| 显式概念关系与规则推理 | SKOS 区分直接上下位关系与关联关系，并单独定义传递层级属性；RDFS 明确定义子类及实例关系的语义。[SKOS §8](https://www.w3.org/TR/skos-reference/#semantic-relations)、[RDFS §3.4](https://www.w3.org/TR/rdf-schema/#ch_subclassof) | 预设关系可由人工选择或由明确字段映射生成。规则推理可以确定执行，但前提必须成立，且只推导规则允许的结论；任意“相关”不能沿路径自动传递。 |
| CSV／关系表映射 | R2RML 由映射作者确定关系数据库到 RDF 的结构与目标词汇，支持逻辑表和外键连接；CSV 到 RDF 标准规定表格及元数据的转换规则，并明确转换不要求检查语义一致性。[R2RML](https://www.w3.org/TR/r2rml/)、[CSV→RDF §1](https://www.w3.org/TR/2015/REC-csv2rdf-20151217/#intro) | `from_id, relation, to_id` 能直接转换为边。转换成功只说明映射执行了，不能证明知识关系正确。CSVW Primer 可作入门，但它是 Working Group Note，不能当作规范推荐标准。[CSVW Primer](https://www.w3.org/TR/tabular-data-primer/) |
| JSON 映射 | JSON-LD 是 JSON 形式的关联数据序列化，使用上下文把术语解释为标识符；1.1 推荐标准为 2020 年，文中链接其 2014 年 1.0 版本。[JSON-LD 1.1](https://www.w3.org/TR/json-ld11/) | JSON 只要显式保留节点 ID、关系和资料关联即可作为本项目交换格式；普通 JSON 并不会自动拥有统一语义，JSON-LD 也不会自动读懂自由文本。 |
| 词典与模式匹配 | spaCy `PhraseMatcher` 适合已知词表的精确短语匹配；`EntityRuler` 可将多个模式关联至同一 ID。官方文档区分规则匹配与训练统计模型，并指出分词和模式不一致会不命中。[Rule-based matching](https://spacy.io/usage/rule-based-matching) | 可确定识别已有知识点被提及的位置。识别到两个名字不等于识别了二者的关系。采用 POS、依存等模型预测特征的“规则管线”，已包含统计模型。 |
| 词项共现和关联分数 | Church 与 Hanks 的 1990 年论文已经利用语料共现与互信息估计词关联。[原始论文 PDF](https://aclanthology.org/J90-1003.pdf) | 同文、同段、同句共现可作为候选关联或检索信号；单篇混合学习笔记可能同时有 Docker 和 MySQL，不能因此生成“Docker 依赖 MySQL 锁”等事实。 |
| 普通全文检索 | SQLite FTS5 支持词项、前缀、短语、近邻和布尔查询，并有排序、摘要和高亮；官方记录其从 SQLite 3.9.0（2015-10-14）起纳入 amalgamation。[FTS5](https://sqlite.org/fts5.html) | 可以先搜索知识点标题、别名、笔记内容与资料元数据。存了一个链接，不代表已经索引链接目标的网页、视频或 PDF 内容。 |

## “不用大模型”需要进一步说清楚

建议在后续访谈中使用三层能力表述，以免把不同技术混为一谈：

1. **确定性基础路线**：手工输入、Markdown/CSV/JSON 解析、显式关系字段、字符串与词典匹配、数据库过滤与全文索引。相同输入与相同规则能重复得到相同结果；不需要训练模型，也不需要生成内容。规则可能属于广义符号 AI 的历史范畴，因此不必声称“绝无 AI”，只需明确实现机制。
2. **传统 NLP／统计机器学习扩展**：命名实体识别、关系分类、统计分词、词向量相似度等；不依赖生成式 AI，但会使用训练数据和预测，可能误识别。spaCy 官方将 NER 明确描述为统计实体识别，并说明效果依赖训练样本、可能需要调整。[spaCy Named Entity Recognition](https://spacy.io/usage/linguistic-features#named-entities)。它不天然适用于“进入容器终端”这类操作知识点，也不自动输出资料关联，适配效果需要样本验证。
3. **生成式 AI 扩展**：解释省略内容、提出别名或关系、改写检索问题等。此层可以后续加入，不是基础图谱的必需输入。保存、展示和采用方式仍待用户决定。

四种“产生关系”的过程应分开描述：

| 过程 | 例子 | 能说什么 |
|---|---|---|
| 显式关系 | 用户写出 `K2 所属主题 K1` | 用户声明了指定关系；系统可忠实保存。 |
| 结构映射 | `##`、列表缩进转为 `结构上位于` | 结构位置确定；语义要另行约定。 |
| 共现 | K1 与 K3 同时出现在 N1 | 有共同出现证据；只能证明同现。 |
| 语义推断 | 模型把省略句解释为“某操作使用某技术”；或形式规则由子类推导实例类型 | 模型判断有不确定性；形式规则结论受前提与规则约束。两类推断都应与原文显式声明区分。 |

## 一个共同样例与三条起步路径

以下是**为研究演示而拟定的格式**。其中 ID、字段和关系名并非已批准规范，也不是 Obsidian 等产品原生支持的统一语法。`example.org` 是占位资料，不代表已核验的教程内容。资料在知识点内逐条指定，因此不需要任何来源继承假设。

```markdown
# 学习摘记 N1
来源清单：
- S1 https://example.org/docker-lesson（学习视频）
- S2 https://example.org/container-exec（参考网页）

## K1 Docker
类型：主题
资料：S1

## K2 进入容器终端
类型：操作
别名：容器终端；进入容器
所属主题：K1
资料：S1；S2

## K3 MySQL 锁
类型：主题
资料：待补
```

三条路径均从同一段样例出发；区别是人工整理的颗粒度与机器转换负担，均可以完全不调用生成式模型。

| 路径 | 输入处理 | 节点和关系 | 资料关联与搜索结果 | 局限 |
|---|---|---|---|---|
| A：人工“一知识点一页” | 人工将 K1、K2、K3 拆为三页，将 K2 的所属主题改为可点击的 K1 链接，保留 N1 原笔记 | 三个知识点页；显式页面链接；若需要区分关系类型，写出“所属主题”文本或固定属性 | K2 页明确列 S1、S2；搜索标题、别名或文字“容器终端”打开 K2，再点资料 | 改造旧笔记需要人工；原生页面链接图通常只记录链接，不能自动成为可查询的类型关系。 |
| B：结构笔记确定性映射＋普通检索 | 约定每个二级标题为一个带稳定 ID 的知识点；只映射显式 `所属主题`、`资料`、`别名` 字段 | K1、K2、K3；保留 N1 及各条目定位；K2→所属主题→K1；不为同文 K3 自动增加知识关系 | 别名词典中“容器终端”→K2，展示 K2、所属主题 K1、N1 的条目和 S1/S2；K3 显示资料待补 | 需要少量约定和解析器；遗漏的字段保持未知，不替用户补关系。 |
| C：CSV／JSON 三表维护 | 人工或确定性转换样例为知识点表、知识关系表、资料关联表；另保留资料元数据和笔记定位 | 知识点表 3 行；关系表 1 行 `K2,所属主题,K1`；资料关联表 3 行 `K1,S1`、`K2,S1`、`K2,S2` | 过滤标题/别名得到 K2，再按 ID 连接资料表返回 S1/S2；以后可映射 RDF 或导入图库 | 数据更明确，但维护表格、外键与重复导入规则需要额外约定；首版未必值得引入独立图库。 |

示例中的 N1 是学习笔记，S1/S2 是原始资料。它们可以存为独立记录，也可以作为与知识点关联的外部对象；不应在知识点总数中混算为两个新概念。三条路径的共同最小结果为：

```text
知识点：K1 Docker（主题）
        K2 进入容器终端（操作；别名：容器终端、进入容器）
        K3 MySQL 锁（主题）
知识关系：K2 --所属主题--> K1（显式字段）
资料关联：K1 -> S1；K2 -> S1；K2 -> S2
笔记定位：K1/K2/K3 -> N1 对应条目
不生成：K1 与 K3 的语义关系；K3 的资料；视频/网页正文中的隐藏知识
```

自然语言查询“怎么进入 Docker 容器终端”也可以先用手工别名子串匹配识别“容器终端”，返回 K2。这是可解释的词典命中，不能称作理解所有自然语言问法。查询“怎么进去那个运行中的东西”若没有命中别名或词项，基础路线应返回无结果或提示修改关键词。

更接近现有材料的极简 TXT：

```text
https://example.org/lesson
1. Docker
2. 进入容器终端
3. MySQL 锁
```

在尚未约定来源继承和语义关系时，确定性导入可以得到三个候选知识点、原笔记的行号和一个笔记级来源，供用户复核；它不能可靠给出“第二项属于第一项”，也不能断言视频支持全部三个知识点。即使先只把知识点关联到原学习笔记，也已经能改善定位，资料分配可在后续访谈中决定。

## 检索实现的一个容易忽略的问题

SQLite `unicode61` 默认按 Unicode 类别将连续字母／数字等视为词元，并不是中文词语切分器。`trigram` 可以支持一般子串检索，但少于三个 Unicode 字符的全文查询不命中。因此不能仅写“有全文索引”就宣称“中文检索已解决”。[FTS5 Tokenizers](https://sqlite.org/fts5.html#tokenizers)、[FTS5 Trigram](https://sqlite.org/fts5.html#the_trigram_tokenizer)。

建议先验证（研究建议）：标题／人工别名精确匹配，加小数据量的子串查找，必要时再引入中文分词或字符 n-gram。若选统计分词或语义向量，要如实将其列入模型能力，而不能混入“纯规则”描述。该建议尚未经过本项目数据集性能验证。

## 应带回访谈的少量问题

1. 用户更愿意每知识点一页，还是在同一篇笔记中为知识点保留少量显式字段？这决定人工录入与解析的边界。
2. 最少需要哪种知识关系？仅“所属主题”是否已足够，还是第一版只要知识点与笔记／资料关联即可？
3. 极简 TXT 的文首来源如何分配：只保留笔记级、导入时人工选择、还是明确采用某种继承规则？本次研究不替用户选择。
4. 相同标题如何处理：要求用户选择稳定 ID，还是先保留不同候选，再人工合并？搜索首版是否接受标题／别名／关键词，而不承诺所有自由问法？
