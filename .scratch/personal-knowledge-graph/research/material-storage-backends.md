# 文件资料本体：三类存储后端比较

核验日期：2026-11-07（Asia/Shanghai）。本文应用 research 技能，读取最新 [spec.md](../spec.md)、[CONTEXT.md](../../../CONTEXT.md) 与 [ADR 0002](../../../docs/adr/0002-postgresql-source-neo4j-projection.md)，核验 Rust、PostgreSQL 与 Amazon S3 官方资料。仅比较存储类别，不选择具体对象存储产品，不建立资料目录、不安装部署、不实现上传。

后续决定（同日）：用户明确要保存 PDF、图片、文档及单文件 1–2 GB 本地视频，副本主要用于查看，不要求外部编辑或移动改名；随后已选择对象服务，本地自部署或云端可配置，见 [ADR 0003](../../../docs/adr/0003-use-configurable-object-storage.md)。该视频数值不是容量上限，以下保留三类后端的历史技术比较，最新状态见 [技术记录](../technical-design.md)。

## 1. 先区分资料记录与文件字节

用户已经确认：PostgreSQL 保存正式结构化业务数据，Neo4j 提供可重建图表示；PG 提交后确认保存，图更新另有状态；Neo4j 暂不可用时继续核心保存、检索与资料打开。这些选择**没有决定文件本体必须塞进 PG，也没有决定本体一定在本机目录**。

资料记录负责“这是哪份资料、与哪些知识点关联、通过什么内部引用找到本体”等正式信息；文件本体是 PDF、视频等实际字节。PG 权威管理资料元信息与关联，本体由目录、PG 二进制存储或对象服务承载，三者均能与已选方案 A 相容。内部存储引用如何设计，仍待实现设计；它不等于用户选择文件时的原始路径，也不必是永久可公开访问的 URL。

已确认业务边界保持如下：

- 作为文件资料上传时，系统保存文件本体，不能仅记住用户电脑上的原路径而依赖原文件一直存在。
- `description` 是知识点属性，不作为上传附件或独立文本资料处理。
- 外部链接只保存地址和关联；网站失效后不归档或恢复完整内容。
- 删除知识点不连带删除上传资料文件；采用哪种后端都不改变这一规则。
- 导入导出与备份恢复细节暂缓，本报告只说明不同后端的架构责任。

## 2. 三类候选一览

| 项目 | 应用管理的本机目录 | PG `bytea`／Large Objects | S3 兼容对象存储服务 |
| --- | --- | --- | --- |
| 本体在哪里 | 应用管理的文件集合中；复制／接收成功后由系统持有 | PG 数据库内部的二进制字段或专门大对象结构中 | 独立对象服务的对象中；可自部署，不必等于公有云 |
| PG 保存什么 | 资料元信息、关联及能解析到受管文件的稳定存储引用 | 元信息、关联和实际字节；Large Objects 还涉及大对象引用 | 资料元信息、关联及对象的稳定存储引用 |
| PDF／视频等大文件 | 可流式读取、定位和分段处理；仍受磁盘、文件系统与实现限制 | `bytea` 与 Large Objects 能力不同；大对象有专门流式／随机访问接口 | 可比较分片上传、对象下载及 Range 等能力，实际兼容性由产品核验 |
| 与元信息一起提交 | 普通文件写入不自动加入 PG 事务 | 同一个 PG 事务可协调相应数据库内写入 | 对象上传不自动加入 PG 事务 |
| 服务与运行时成本 | 无额外对象服务；应用负责文件管理、打开与失败处理 | 无额外存储服务，但数据库负载与本体管理耦合 | 多一个服务或外部依赖，需要连接、权限、运行和存储配置 |
| 数据体积与恢复责任 | PG 主要保存结构化记录；完整资料还包括文件集合 | 数据库同时承载元信息与文件字节，需要覆盖所选大对象形式 | PG 记录与对象集合都属于完整资料范围 |

表中职责划分与适用判断为本项目推断，技术能力来源在下文。PDF 并不必然小，视频也不必然大；应按实际文件大小和读写方式比较，不按扩展名设置未经确认的容量门槛。

## 3. 候选一：应用管理本机目录

Rust 标准库提供文件复制、文件读取、写入及定位能力。`std::fs::copy` 复制实际内容并返回结果，可能因源文件不存在、权限或目标条件等失败；`File` 实现读取、写入与定位接口。因此本机受管文件可以按流／分段处理，不需要因为上传一个大文件就必然把全部内容装进内存。[Rust file copy](https://doc.rust-lang.org/std/fs/fn.copy.html)、[Rust File](https://doc.rust-lang.org/std/fs/struct.File.html)。

**本项目候选设计：** 选择文件后将本体接收到应用管理的文件集合，PG 保存正式资料记录与内部引用。系统之后通过该引用定位自己的副本，而不是每次回到用户原来的下载目录。这体现“保存本体”，不代表已经选择 Windows 的哪个目录、固定盘符、文件命名、内容哈希、去重或是否允许用户移动目录。

这条路线适合更看重单机直接使用、希望不再增加对象服务的情况。文件打开可以由应用读取受管本体，或按后续交互设计交给合适的查看程序；“使用普通文件”不等于预览器、视频拖动或所有格式打开行为都已经验证。

成本在于文件与 PG 是两个持久化边界：文件接收中断、PG 写入失败、存储引用失效都需要正确处理。稳定存储引用用于保持应用层身份，不等于永远不需要处理磁盘迁移或文件存在性；本文不设定相应流程。

## 4. 候选二：把字节保存在 PostgreSQL

### `bytea` 与 Large Objects 不能混为一项能力

`bytea` 是用于保存原始二进制字符串的字段类型。PostgreSQL 官方另有 Large Objects 机制，专门提供类似文件的流式访问；官方说明 TOAST 字段最多约 1 GB，Large Objects 可达 4 TB，后者也支持局部读写。它们是当前文档中的引擎上限，不是本产品建议的文件大小，也不是目标 Rust 驱动与安装环境的性能保证。[PostgreSQL binary types](https://www.postgresql.org/docs/current/datatype-binary.html)、[Large Objects introduction](https://www.postgresql.org/docs/current/lo-intro.html)、[Large Objects streaming](https://www.postgresql.org/docs/current/largeobjects.html)。

因此，不能把“PG 支持 bytea”直接推广成“任意多 GB 视频可按普通字段无差别处理”；也不能声称“数据库完全不能存视频”。若比较 PG 内存储，应分别验证 bytea 与大对象接口，特别是实际文件大小、流式操作、随机读取和客户端内存行为。普通 TOAST 字段的许多操作按完整值处理，大对象为局部访问提供专门机制；这不是声称 bytea 绝无任何分段实现方式。[Large Objects comparison](https://www.postgresql.org/docs/current/lo-intro.html)。

### 一致性收益与运维代价

元信息与 `bytea` 字段可以在同一个 PG 事务中保存；Large Object 接口的操作同样需要事务范围，其描述符有效期与事务相关。由此可以设计数据库内的本体和元信息共同提交，避免普通外部文件不在 PG 事务中的那类窗口。客户端 API、实际事务组织与失败回滚仍需验证，不能只看数据类型就假定应用自动正确。[PostgreSQL BEGIN](https://www.postgresql.org/docs/current/sql-begin.html)、[Large Object interfaces](https://www.postgresql.org/docs/current/lo-interfaces.html)。

Large Objects 有独立对象及引用的生命周期。官方专门说明，删除引用记录不等于自动删除大对象，可能留下没有引用的大对象。这是需要正确管理的技术边界，不是本项目立即启用自动清理的理由；已确认的“删节点不删上传文件”仍适用。[PostgreSQL large-object management](https://www.postgresql.org/docs/current/lo.html)。

**条件建议：** 若特别重视本体与元信息处于同一个数据库事务域，并接受资料字节增加数据库存储和读写负担，可深入比较 PG 内存储。若资料长期以较大视频为主，Large Objects 的流式能力值得评估，但不能因其上限足够就略过数据库体积、连接和长时间传输的成本。本文不默认选择 bytea、Large Objects 或文件大小切换规则。

## 5. 候选三：S3 兼容对象存储服务

这一类别把资料字节交给独立对象服务，PG 保存资料记录及稳定对象引用。服务可在用户自部署环境运行，也可由其他服务方提供；选择 S3 接口类别不等于已经接受云端保存个人资料，也不意味着必须公开对象。

以 Amazon S3 官方 API 作为能力参考：multipart upload 将一个对象分成多个部分，部分可分别上传和重试，完成后组成对象；GetObject 支持按字节范围读取。这些机制适合比较大文件上传和部分读取需求，但不能仅凭接口名保证某个“S3 兼容”实现具有完全相同的限制、错误行为或性能。[S3 multipart upload](https://docs.aws.amazon.com/AmazonS3/latest/userguide/mpuoverview.html)、[S3 GetObject](https://docs.aws.amazon.com/AmazonS3/latest/API/API_GetObject.html)。

后续产品核验需要确认本项目会使用的上传、下载、Range、分片、认证和持久化能力；本报告不列具体产品，不代替该核验。对象服务提供读取接口，也不自动完成桌面 PDF 预览、外部播放器调用或浏览器视频播放适配。

PG 应保存可长期解析的对象引用；若采用有期限的访问 URL，应按需要生成，不能把临时签名地址误当永久资料标识。AWS 官方明确签名 URL 受其期限和签名凭证有效期限制；兼容产品的相应行为也需逐项检查。[S3 presigned URLs](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html)。

**条件建议：** 若希望资料存储成为独立服务、需要标准对象接口，且愿意承担额外服务配置，这一类别值得比较；用户已经接受 Docker，使其部署形式可以进入讨论，但不自动证明它优于本机受管目录。对象服务仍通常依赖其底层磁盘或卷，“服务化”不会让文件保留责任消失。

## 6. 保存完成与失败状态应讲清楚

Q14 已确认“PG 提交即确认，图更新另记状态”，这解决结构化业务与 Neo4j 投影的关系，**不能用来宣布尚未可靠接收的附件已经保存完成**。选择资料文件后，PG 可能先记录接收中的资料，也可能在本体接收完成后才正式登记；具体策略尚未决定。无论采用哪种顺序，本体未完成时都不能将其展示为已就绪并可正常打开。

| 发生的事 | 架构上必须承认的状态，不预设具体界面 |
| --- | --- |
| 本机复制或对象上传失败 | 资料本体尚未保存完成，需要保留真实错误与可处理状态，不能因 PG 有一条记录就显示成功 |
| 本体成功，但 PG 事务失败 | 存在尚未被正式资料记录接纳的字节，需要有后续可识别的处理责任，不立即默认删除或去重策略 |
| PG 已登记，但本体操作中断 | 资料记录与本体状态不一致，不能作为可打开的就绪资料；需能正确重试或修正 |
| PG 与本体已完成，Neo4j 更新滞后 | 正式资料保存与图投影更新分别记录；遵守已确认的核心功能继续使用方向 |

外部文件操作和对象请求不会仅因 PG `COMMIT` 就自动成为同一原子事务。PG 内 bytea／Large Objects 可通过相应 PG 事务组织获得不同的一致性边界，但仍需检查实际操作完成结果。上述状态是正确性分析，不是在本轮规定上传步骤、状态字段、消息队列或补偿实现。[PostgreSQL transaction scope](https://www.postgresql.org/docs/current/sql-begin.html)、[Rust copy result](https://doc.rust-lang.org/std/fs/fn.copy.html)、[Large Object transaction scope](https://www.postgresql.org/docs/current/lo-interfaces.html)。

## 7. 仅保留备份架构责任，不展开流程

- **本机目录：** 完整资料包括 PG 元信息及对应受管文件，单独保存数据库不包含这些外部字节。
- **PG 内存储：** 数据库需要同时承载资料字节；未来恢复设计必须覆盖实际采用的二进制字段或大对象，不能只处理业务表元信息。
- **对象服务：** 完整资料包括 PG 元信息及对应对象，两个系统各自存在不等于恢复时引用自然匹配。

以上是由存放位置推导的责任分工。本报告不决定备份频率、保存位置、打包格式、保留数量或恢复步骤，也不将它们新增为当前交付要求。

## 8. 当前仍待选择

三类方案都能满足“PG 权威管理资料记录、系统保存上传文件本体”；真正要决定的是文件字节的承载位置与愿意维护的复杂度。

- 更重视本机直接访问、减少额外存储服务：优先比较应用管理目录。
- 更重视字节与元信息进入同一 PG 事务域：比较 bytea 与 Large Objects，同时接受数据库承担本体体积。
- 更重视独立对象服务和通用接口：比较 S3 兼容类别及具体实现。

后端、目录、路径组织、去重、内容哈希、文件版本、容量限制、对象产品及迁移方式均未由用户确认。技术文档不应把此前“普通文件”候选建议或“PG 是事实源”改写成文件本体已定存储位置。
