# 图数据归属：关系主库与图主存的公开实践

核验日期：2026-11-07（Asia/Shanghai）。本文是独立研究，用于公平比较已确认 PostgreSQL＋Neo4j 组合中的职责分工；不修改业务稿、技术设计或已确认产品偏好。

后续决定（同日）：用户已选择 A：PostgreSQL 保存完整正式事实，Neo4j 为可重建图查询副本，见 [ADR 0002](../../../docs/adr/0002-postgresql-source-neo4j-projection.md)。以下案例和条件判断保留为当时的比较依据，不表示 B 仍为当前待选方案，也不改变对其适用性的评价。

## 先区分两个问题

“每项业务事实有明确负责人”不要求所有数据都只能以同一个数据库为负责人。

- **A：关系库为事实源，图为派生查询副本。** 知识点与关系先正式保存在 PG；应用自动同步需要的部分到 Neo4j。物理上会保存两份相关数据，使用者只操作一次，程序负责同步及故障处理。
- **B：图领域由 Neo4j 负责，PG 负责另一些业务对象或记录。** 知识点名称、description、所属主题与图内有效/回收状态可以统一由 Neo4j 负责；PG 不必再保存另一套可写的同名知识数据。但跨库引用和跨对象操作仍需明确。

二者都需要清楚的数据所有权。A 的重复保存主要是自动派生；B 的重点是划分事实归属，不能随意将一个知识点的各个字段拆散。业务 API 可统一由 Tauri Rust Core 提供，不意味着用户需要到两个数据库各手工维护一次。

## 三条一手材料

### 1. A 的明确架构示例：关系主系统同步到 Neo4j

Neo4j 官方开发者文章《Data migration between MySQL and Neo4j》，发布日期 **2013-04-26**，明确将现有 MySQL 留作主记录系统，Neo4j 保存较小数据子集，分别服务近实时业务查询或批处理。文章描述初始加载，以及主系统发生变化后用事件同步图；图实体使用主系统 ID 对应原始实体。[官方文章](https://neo4j.com/blog/developer/data-migration-between-mysql-and-neo4j/)。

**证据范围：** 这是直接说明 A 的历史架构示例，来源使用 MySQL，不是 PG；不是本项目相同技术栈的现网客户盘点，也不能据其旧代码确定当前驱动或同步工具。文章本身强调已有关系主系统和增加图能力的背景，不能将这个背景自动套给尚无应用实现的新项目。

**条件观察（推断）：** 已有关系主系统承担业务写入、图是其关系增强视图，或图要整合多个既有来源时，A 的职责自然。图的可见性、延迟与同步失败需要明确设计，不因它是公开模式就自动获得一致性保证。

### 2. 图作为运营记录核心：BT Group 的 SRIMS

Neo4j 官方客户材料介绍，BT 以 Neo4j 重建 SRIMS 网络库存管理平台，目标是统一的运营记录及端到端规划；原图数据库的接口层迁移到 Neo4j，并通过 API 与其他业务系统集成。材料将其作为关键运营支持系统的一部分，不只是离线图分析展示。[BT Group 官方客户材料](https://neo4j.com/customer-stories/bt-group/)。页面未明确标注发布日期；本次核验可访问。

**证据范围：** 支持“图数据库可以承担正式业务记录和运行时操作”这一判断。材料没有给出 PG 保留何种职责的完整数据归属表，因此不能称为已证明“Neo4j 主知识＋PG 资料元信息”的精确 B 组合，也不能扩大为 BT 全公司的所有数据都在 Neo4j。

**条件观察（推断）：** 当业务对象及其连接本身就是运营模型，业务代码围绕图直接维护与查询时，Neo4j 作图领域主存有充分依据；不应把图库只能作副本当成既定原则。

### 3. 知识图在运行时被更新：Infinitus

Neo4j 官方客户材料介绍，Infinitus 原先用 PostgreSQL 的 JSON 存储医疗保障规则，后将该规则知识层转向 Neo4j。运行时流程先查询图；遇到缺失或陈旧答案时，系统通过电话取得新资料，再更新图供后续请求使用。[Infinitus 官方客户材料](https://neo4j.com/customer-stories/infinitus/)。页面未明确标注发布日期；本次核验可访问。

**证据范围：** 证明这是参与业务决策并接受新知识更新的图应用，不是只能从关系库定时复制后做分析的例子。材料未说明迁移后 PG 是否仍负责其他对象，也未给出全部权威数据归属与同步协议，不能借此编造完整 B 方案。本文不将其客户性能数字推广为“B 总是更快”。

## 产品能力的补充依据

当前 Neo4j 官方资料明确其图存储与 ACID 事务能力；官方培训也直接展示以 Neo4j 为主数据库的应用架构。旧培训用于说明该架构类别已有正式材料，不用于推荐旧数据库版本。[当前产品与存储说明](https://neo4j.com/docs/getting-started/whats-neo4j/)、[当前事务说明](https://neo4j.com/docs/operations-manual/current/database-internals/)、[官方主数据库架构示例](https://neo4j.com/graphacademy/training-admin-35/02-neo4jadmin-3-5-overview-neo4j-admin/)。

Neo4j 也支持为字符串属性建立全文索引，名称与 description 搜索不要求必须另存到 PG。这只说明能力可选；中文匹配、排序和实际效果仍需按业务规则验证。[官方全文索引说明](https://neo4j.com/docs/cypher-manual/current/indexes/search-indexes/full-text-indexes/)。

## 本项目应怎样比较

当前业务的知识点名称、description、主题多归属、资料连接及图内回收状态高度关联；所有操作来自同一使用者。核心目标仍是查找知识并阅读描述、打开资料。以下是结合公开材料和当前需求的设计判断，不是来源给出的唯一答案。

| 判断点 | A：PG 事实源＋Neo4j 投影 | B：Neo4j 图领域主存＋PG 其他职责 |
| --- | --- | --- |
| 图知识正式保存在哪里 | PG；Neo4j 中的相应数据由程序生成并更新 | Neo4j；PG 不再保存另一套可编辑的同一知识事实 |
| 是否保存部分重复数据 | 是，ID、必要属性与边会在图副本再保存；用户不重复录入 | 不要求复制同一知识数据；跨库引用通常仍需要稳定 ID |
| 一次知识编辑的事务 | 正式业务修改可在 PG 内完成；图何时更新需要同步策略 | 若名称、描述、主题边及相应回收状态同放图内，纯图维护可在 Neo4j 事务内完成 |
| 主要额外责任 | 映射、重复投递处理、失败重试、图可见性和重建 | PG 的独立职责边界、跨库引用及真正跨两类对象操作的部分失败 |
| 何时自然 | 已有或明确需要 PG 为正式关系模型；图是增强视图或多源聚合结果 | 知识对象与关系是直接被用户维护的领域，相关变动可由图内事务统一负责 |
| 不能默认的行为 | 用户已接受图延迟、图失败时仍然保存、图永远只读于主流程 | 用户已接受跨库操作的部分成功；PG 只是任何“不像图的字段”的收纳处 |

尤其不应先把 description 放在 PG、所属主题放在 Neo4j，再以修改知识点需要跨库为由笼统判定 B 代价过高。可先把知识点及其核心关联作为一组图领域数据，再判断资料元信息、必要导入记录等放在哪里。若某项操作确实跨库，仍须定义结果与补偿；B 不会自动消除所有一致性问题。

如果 PG 目前没有独立且值得保留的职责，**Neo4j 单库**是解释取舍的第三个有效对照：它可以让图、描述、资料元信息和管理状态共处一个业务存储。提出这个对照不撤销用户对 PG＋Neo4j 的已确认兴趣；它有助于明确保留 PG 换来什么价值，也不扩展到其他产品。

## 研究结论与不足

- A 有明确官方架构示例，适合关系主系统增强图能力的条件，不能将其提升为所有新建图应用的默认规范。
- 图数据库承担运行时业务和正式记录有直接客户材料；B 不应预先被判为不成熟或只能用于分析。
- 本次没有核验到与本项目完全相同、完整公布“Neo4j 负责知识领域＋PG 负责资料领域”归属和事务协议的一手客户方案。BT 与 Infinitus 只支持材料明确交代的范围。
- 当前应先确定知识领域数据的权威归属，再讨论真正需要复制或跨库的部分。A/B 均不要求用户手动重复维护，但需要程序承担各自的工程责任。
- 不据本研究要求用户立即选择 A，不新增微服务、消息中间件、部署要求或版本排期，也不展开用户暂缓的导入导出和备份恢复细节。
