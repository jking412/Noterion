## 当前技术方向：Tauri＋Rust＋PostgreSQL＋Neo4j

两种数据库本身均能表达当前需求。结合用户对两种技术的明确兴趣，同时采用是有理由的工程选择；当前业务规模尚未证明它比单库必要或更快，不能编造性能收益。

已选择的数据职责与当前推荐运行形态；运行细节仍需验证：

    Windows 宿主：Tauri 界面 → Rust 应用逻辑
                                  ├─ PostgreSQL：完整正式业务事实与基础检索
                                  ├─ Neo4j：可重建图查询副本
                                  └─ 对象存储：正式文件本体，本地或云端配置
    图同步任务：同一 Tauri/Rust 应用内，读取 PostgreSQL 待办并更新 Neo4j
    Docker Compose：推荐运行 PostgreSQL、Neo4j，以及选择本地部署时的对象服务
    两库之间的数据同步：由应用负责，不由 Compose 自动完成

PostgreSQL/Neo4j 职责及对象存储类别已确认，但系统尚未创建或测试。React/TypeScript 是界面推荐；对象产品、真实配置和备份形式未决定。

### 已选择方案 A：PostgreSQL 为事实源，Neo4j 为可重建图查询副本

| 对象或职责 | 推荐归属 | 说明 |
| --- | --- | --- |
| 知识点 ID、名称、description、当前有效状态 | PostgreSQL | 保存正式业务数据，普通编辑从应用操作进入 |
| 所属主题、资料关联、资料元信息、必要导入记录 | PostgreSQL | 相关业务变化可组织在同一 PostgreSQL 事务内；具体表结构及操作边界待规则明确 |
| 回收站及恢复所需正式信息 | PostgreSQL | 以业务规则决定状态，不让投影丢失决定数据已被删除 |
| 用于邻接、关系浏览及路径查询的节点与边 | Neo4j | 同步必要稳定 ID、关系及展示/查询字段，承担实际图查询 |
| 原始资料文件本体 | 对象存储服务 | 本地自部署或云端配置，PG 存正式资料记录和稳定引用；不把文件字节重复塞入图数据库 |
| 改动同步记录 | PostgreSQL＋Rust 后台处理 | 提议和业务变化一并记下待同步信息，再由应用可靠投递到 Neo4j |

“事实源”表示发生冲突时以它为准；“可重建副本”表示图数据库的数据可根据正式记录重新生成。这不妨碍使用 Cypher 做真正的图查询，但不把应用以外直接修改 Neo4j 的内容视为自动保存到正式业务数据。

用户在完成 A/B 比较后明确选择本方案，理由是需求仍在细化，希望完整正式事实集中在 PostgreSQL，避免过早拆分两个权威数据源。用户只编辑一次，应用自动维护图副本；重复的是部分存储表示与同步工程，不是要求人手工编辑两遍。此选择不代表数据库已提供现成自动同步。依据见 [ADR 0002](../../docs/adr/0002-postgresql-source-neo4j-projection.md) 与 [双库研究](./research/dual-database-design.md)。

### 比较记录：方案 B（本次未选择）

该方案让 Neo4j 保存知识点及其 name、description、所属主题关系和相应图内回收状态，PostgreSQL 保存独立的资料元信息及其他明确的关系业务数据。每类事实仍有唯一权威方，B 不等于让同一知识点在两库各保留一份可独立修改的正式版本。

在此清楚边界下，创建知识点、修改 description、调整所属主题，乃至按规则删除/恢复图内节点，都可设计为只访问 Neo4j 的事务。不能将 description 先拆到 PostgreSQL，再以人为制造的跨库操作判定 B 普遍不合适。若资料关联归 Neo4j、资料元信息归 PostgreSQL，应明确用稳定 ID 对应；此处仅为比较假设，未确定关联归属。

新增资料并关联到知识点、维护跨库引用等操作可能涉及两库，需处理部分完成、重试和协调；普通 PostgreSQL 事务与普通 Neo4j 事务不会自动合并。B 的主要成本在边界处的协作，A 的主要成本在派生复制、同步与新鲜度，两者不能仅以“跨库”二字统一排名。

### 同步与一致性的必要边界

- 已选 A 需要可靠记住正式变化与图更新的对应关系。推荐在 PostgreSQL 内将业务变更和待同步记录一起提交，再由 Rust 后台处理图更新；具体投递实现仍为工程建议，不将两库分别写入视作同一次原子提交。
- 可借鉴事务性 outbox 模式；这是组织数据库记录与应用任务的模式建议，不要求引入 Kafka、CDC 服务、消息中间件或独立同步微服务。
- Q22 已选择同步任务随桌面应用运行：完全退出后停止处理，待办仍在 PostgreSQL，下次启动继续。不为退出后的持续投递增加独立 worker；具体轮询、批次及关闭处理属于工程设计。
- 后续需设计稳定应用 ID、重复投递幂等、顺序/版本检查、失败重试、删除/恢复信息及全量重建；本轮只登记责任，不确定具体 schema 或工具。
- Q14 已确认应用先完成 PG 正式保存，图查询副本随后更新并显示独立更新状态；具体等待、刷新和同步时限仍待实现设计。
- Q15 已确认 Neo4j 临时不可用、其他所需组件正常时，继续核心读写和资料访问；图功能明确不可用，副本恢复并赶上变化后再恢复。不能把图查询失败显示为无关联。
- Docker 可以统一运行环境与持久化配置，不能替代跨库同步、正式数据权威或一致性设计。
- 数据库卷不等于应用完整备份；两库与外部资料的恢复责任仍存在，但按用户当前范围不展开备份恢复细节。

## 第六轮：保存与图查询副本可见性（两题均已选 A）

用户已分别回答 Q14=A、Q15=A。以下记录实际选择，不再重复征询这两项政策。

### Q14：正常保存是否要等待图更新完成？

已确认：PostgreSQL 正式保存完成后就确认“已保存”，描述与列表采用最新正式数据；图查询副本尚未更新时明确显示“图谱更新中”，不能把旧图当作最新正式状态。是否需要等待同步后再刷新图、是否用当前操作的正式结果更新已加载界面，属于后续实现设计，不以本选择承诺未经验证的即时图效果。

未选择正常保存都等图更新完成的政策。若 PostgreSQL 已成功而图更新失败，仍须准确说明正式保存已完成、图更新未完成，不能报成“完全没保存”。

状态：已确认 A；具体超时、刷新方式和同步时限未定。

### Q15：Neo4j 临时不可用，是否允许继续使用核心数据？

已确认：PostgreSQL 及其他相应组件可用时仍可保存正式知识、搜索名称/description、查看详情及资料；图查询入口明确不可用或更新待恢复，变更保留待同步。不能将失败的图查询伪装成“无关联”或“知识点不存在”，也不默认用旧图假装已恢复最新状态。

未选择要求两库都正常才允许核心操作的政策；已有 PostgreSQL 提交必须如实反映。

这是用户已确认的服务异常例外；正常状态仍实现“搜索结果点击后在图谱定位”。恢复不能仅检查连接成功，还需确认图副本赶上正式变化。

状态：已确认 A；未引入离线模式、独立常驻同步服务或额外部署要求。

## 对象存储的工程收敛

已确认的类别与工程建议分开记录：对象服务类别、本地或云端配置空间是用户选择；S3 兼容访问契约、AWS Rust SDK 及具体产品是工程核验和推荐范围，不把支持类别写成任意厂商已经通过兼容测试。

- 推荐 Rust Core 通过 S3 兼容接口访问对象。配置至少区分 endpoint、region、bucket、凭据和地址风格；本地与云端可以复用接口，但差异不保证仅改一个 URL 就可完全迁移或互换。
- PG 保存资料身份、元信息、就绪状态与稳定对象引用；签名访问 URL 在需要时生成，不作为永久对象标识。
- 对象长期访问凭据由 Rust 侧处理，不交给界面长期持有；界面读取可用受控临时地址或受控转发，具体路径按服务能力验证。
- 大文件需验证分片上传、范围读取、签名、CORS/响应头和客户端校验行为；不要求用户逐项挑 SDK 或输入尚未确定的真实凭据。
- 上传对象未完成或 PG 正式记录未成功时，资料不得被标为已就绪。Q14 的 PG 保存确认与 Q15 的图库降级不免除此要求。
- 对象副本主要查看，不增加自动转码、自动跨本地/云端同步或公开共享要求。具体云端服务在真实配置时确定；当前未部署或外发资料。

工程方案收敛为：Rust Core 封装 AWS 官方 Rust S3 SDK，按配置访问本地或云端 S3 兼容服务；不是要求使用 AWS 云。自定义端点不保证完整兼容，实际所需分片、Range、签名、校验及错误处理按所选服务固定版本验证。

本地参考部署有界推荐 RustFS，Garage 保留为对照；此建议基于当前所需接口和集成文档，并非两者长期可靠性的实测排名。具体本地产品不阻塞检索等独立技术分支，云端仍由使用者配置适用的兼容服务。换 endpoint 不自动迁移既有对象，也不能让旧对象引用悄悄指向另一处。

两份研究均已完成：[可配置对象接口](./research/configurable-object-storage.md)、[本地对象产品建议](./research/object-storage-product-choice.md)。未运行任何镜像、创建 bucket 或使用真实云端连接。

官方架构指南提供按场景选模式的原则，不提供“所有 PG＋Neo4j 项目统一选 A”的结论。以下把这些原则映射到本项目，是设计推断，不是行业采用率或性能测量。

| 判断条件 | 更支持 A：业务主库＋图查询副本 | 更支持 B：图权威＋其他数据各自权威 |
| --- | --- | --- |
| 已有系统与数据 | 已有 PostgreSQL 业务系统，图功能是在其数据上增添分析或关联查询 | 从零构建以节点、边及其写入规则为核心的图应用，没有既定 PG 知识主库 |
| 图的作用 | 图是能从其他记录重建的查询表示 | 图是正式业务模型，图内修改本身产生不可丢失的新事实 |
| 常见写入边界 | 经常需要将知识、关系、资料、管理状态放在同一 PG 事务内判断和提交 | 大多数写入是图内节点、属性及边操作，可放在同一个 Neo4j 事务内 |
| 直接写图的期望 | 通过应用修改正式源，图库主要查询；对图库的独立修改不自动成为事实 | 业务操作直接写入 Neo4j，经应用校验后的图变化就是正式数据 |
| 数据重复与同步 | 接受部分数据的自动派生复制，并愿实现投递、重试与重建 | 希望图事实只维护一份，能把图和其他业务的所有权边界划清 |
| 新鲜度要求 | 能接受读副本更新窗口，或应用愿以等待/回源等方式处理 | 核心图编辑后直接在同库读取已提交图；跨域资料仍另有一致性边界 |
| 故障后的依据 | 可以按 PG 重建 Neo4j，图库不保留独有正式事实 | Neo4j 及 PG 各自都可能有不可从对方重建的数据 |
| 主要反例 | 用户产生的新图事实只写 Neo4j，却仍声称可从 PG 完整重建 | name/description/边任意拆散，或者两库都允许改同一事实却没有权威规则 |

两者都需要可靠错误处理；严格跨库原子性要求不能仅靠选择 A 或 B 消失。A 并不强制采用完整 CQRS、事件溯源或消息中间件；B 借鉴按领域分配数据所有权，也不要求将本机应用拆成微服务。

直接官方依据：

- [Microsoft Materialized View](https://learn.microsoft.com/en-us/azure/architecture/patterns/materialized-view)：查询副本由专门组件维护，可从正式数据重建，消费者不直接修改副本。
- [Microsoft CQRS](https://learn.microsoft.com/en-us/azure/architecture/patterns/cqrs)：读写模型分离可在同一数据库内，也可分离存储；要权衡复杂度和新鲜度，简单领域/CRUD 可能不适合。
- [Microsoft 数据管理原则](https://learn.microsoft.com/en-us/azure/architecture/microservices/design/data-considerations)：具体实体有明确权威来源，其他位置可以保存副本；没有单一方法适用所有场景，强耦合边界应重审。
- [AWS Database per Service](https://docs.aws.amazon.com/prescriptive-guidance/latest/modernization-data-persistence/database-per-service.html)：按业务需要选择各自存储，同时承担跨边界查询和事务成本；本文只借鉴所有权原则，不引入 AWS 或微服务部署。
- [AWS Transactional Outbox](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)：业务与待投递记录同事务保存，投递处理重复和顺序；不是把两库共同提交的保证。

本项目映射：尚无已有 PostgreSQL 业务系统，知识点、description 与所属主题均形成连贯的图内操作，B 因而值得正式候选；主题删除与回收站也可在图权威模型内统一设计。若用户更希望 PG 统一管理全部正式知识、Neo4j 专注可重建查询表示，则 A 仍成立。资料元信息与资料关联是否能划清边界，是比较 B 的关键，不能仅凭“个人项目”或“有 description”就替用户决定。

本轮研究已完成：

- [成熟模式与条件矩阵](./research/graph-ownership-patterns.md)：A 自动派生、B 按事实分工、同一事实双主的区别，以及适用条件、反例与项目映射。
- [公开实践与证据边界](./research/graph-ownership-case-evidence.md)：2013 年 Neo4j 官方关系主系统增强图查询的 A 示例；BT SRIMS 与 Infinitus 说明图可承担正式运营记录及业务写入。后二者未披露完整 PostgreSQL 分工，不能称为本项目 B 同栈的精确证明。

比较过程曾修正此前对 A 的单向偏重，承认 B 的图内维护可单库完成。最终用户仍基于需求演进与统一正式事实的考虑选择 A。以上条件矩阵保留为选择理由与未来复评依据，不表示 B 仍为当前待选主路线，也不声称 A 是所有项目的统一最佳实践。

## 其他候选的评估边界

本轮对照单用 Neo4j、单用 PostgreSQL 以及 PostgreSQL＋Apache AGE；可补充 SurrealDB 作为多模型独立产品备选。它们是替代路线，不能把所有候选叠加进当前架构。

- 单用 Neo4j：统一图内的正式数据与事务，若资料元信息、描述与必要记录也纳入同库，可以减少跨库同步；并不强制必须再配一个关系数据库。
- 单用 PostgreSQL：能表达节点、关系、描述及资料关联，当前所属主题和名称/描述检索不因此失去表达能力；不满足本轮希望实际使用 Neo4j 的技术兴趣。
- PostgreSQL＋Apache AGE：在 PostgreSQL 内增加图模型/Cypher 扩展，有少维护一个数据库引擎的潜在收益；不是 Neo4j 的同产品或完全兼容接口，支持版本和 Rust 集成需按当前官方资料核对。
- SurrealDB：官方提供 Rust SDK，支持连接服务实例与嵌入运行，文档和图边共享存储；作为不同多模型路线的对照，需要学习其查询语言并验证本项目所需能力，不承诺它无成本替代 Neo4j/PostgreSQL。[官方 Rust SDK](https://surrealdb.com/docs/reference/rust)、[数据模型架构](https://surrealdb.com/docs/learn/data-models/architecture)。

完整对照见已完成的 [数据库替代路线](./research/database-alternatives-shortlist.md)，不以本节提及视为已经采用。AGE 是 PostgreSQL 扩展，不是独立 Neo4j 服务器；openCypher 支持不等于完全兼容 Neo4j 的协议与工具。
