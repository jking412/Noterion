## 已确认的失败与因果

未取得用户当时的笔记、响应及运行版本，因此本记录不认定其当次究竟缺少来源还是超过八条。

合成最小样本通过真实 `decode` 证实：旧实现对空依据及九条真实依据返回相同的“AI 候选缺少可核对的原文依据”。九条有效引文进入预览的回归先红。通过真实 HTTP → 提取任务的回归进一步复现了用户完整报错；有效候选与缺失来源候选混合、结构修正后缺失来源，均在旧实现第二次调用后失败。证据为 `red-sources.log`、`red-http.log`。两次通用完整重出不能区分来源与业务缺陷，还会重新生成已正确的内容。

真实基线 Windows 客户端同样复现该报错：`issue-34-baseline-recovery-red-02`，两次模型请求，零采用。另一个可见控件回归确认旧页面在修改原文、再还原相同文字后重新允许采用旧草案：`issue-34-baseline-source-red-03`。对应脱敏结果、失败信息和截图固化在 `evidence/`。

验证前的预测是：九条改为八条可通过原数量限制；仅改变原文空白即可使逐字定位失败；结构修正与来源缺陷共用预算会阻断第二种可恢复问题；重试局部失败会重新处理成功分段。回归分别验证了这些机制；并非从通用错误文本反推用户输入。

## 实际修复

- `sources.rs` 集中持有原文片段身份、字节范围、空白映射和来源补丁规则。仅规范化空白；多解、非当前分段、未知身份、身份与文本不符、改写内容均拒绝。最后的引文来自原文切片，UTF-16 范围由程序计算。
- 初次提取不变；来源异常聚合为待修候选，单独要求来源补丁。可选程序提供的 `sourceIds` 或精确 `evidence`，两种方式不能混用。补丁只替换待修依据，拒绝漏项、额外候选、重复身份和偷偷改 Point；原知识、主题和资料引用保持。九条有效依据完整保留，上限 64；超过上限明确分型并修复。
- 结构/业务修正和来源修复各一次，每段最多三次逻辑调用。连接适配器既有最多三次传输尝试、120 秒请求超时、45 秒无流数据超时、任务五分钟上限及取消均保留。鉴权/连接错误不会被当作来源补丁错误继续重出内容。
- 独立规格审查发现合法候选旁的模型 warnings 曾被丢弃：模型已声明漏项也会成为可采用预览。两个真实 HTTP 回归先红（`red-omissions.log`），修正为非空 warnings 使用现有完整修正预算要求完整重提，持续声明未完成则失败，不发布也不缓存该分段；重试须重新请求。结构/身份基础校验统一为 `Output::parse`，消除标准审查指出的重复规则。
- 成功分段只在内存按输入指纹、目录、epoch、revision 缓存，最多最近四份输入；局部最终失败不返回半份草案，不保存知识，重试可复用已完成分段。缓存不写数据库，退出后不保留。全部候选仍执行最终业务校验及显式事务采用。
- `useAiTasks` 固定实际请求与重试的输入副本，保留 generation/取消保护。页面将原文变更标志保持至下一次整理，恢复相同文字不重新启用旧采用；上下文 reset 清除本地候选。删除本次导入页的固定机制小字，不把模型 warnings 或内部校验详情作为用户正文。
